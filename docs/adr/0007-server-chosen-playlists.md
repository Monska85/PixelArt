# 7. Server-chosen playlists

Date: 2026-10-28

Status: accepted

## Context

A board plays one playlist, the one its `playlist` setting names, `default` unless a client changes it. To play Halloween animations in October and Christmas animations in December, someone has to change the setting on every board, twice a year. Content releases ([ADR 0006](0006-content-release.md)) already reach every board on WiFi without a firmware release, so the project could choose the season for every board, if the board knew what to play when.

Some facts shape the solution:

- **Backward compatibility comes first.** Boards running firmware 1.0.0 and 1.1.0, the web apps released with them and `tools/pixelart.py` speak protocol 1 and read manifest format 1. Protocol 1 can grow only by addition ([versions](../protocol/protocol-v1.md#versions)), and every reader ignores manifest fields it does not know (checked on the firmware 1.0.0 with `content_version`).
- **Older clients know only `playlist`.** An older web app shows it as "Active playlist" and sets it with `settings_set`. An older firmware, after a rollback, plays the playlist its stored `playlist` key names.
- **The time is optional.** A board asks for the time only for an install window narrower than the day, and may never get it (no WiFi, a blocked server). It must play something sensible without it.
- **The board is small.** The loop task that plays the animations and answers the protocol has a stack of 8 KB and checks its frame timing; any work it does at a switch must be bounded and short.
- **The user keeps the last word.** Some users want their own choice, whatever the season: a list of playlists, or one of the schedules on the board.
- **The server chooses what Automatic plays, not the board's file names.** A fixed ID such as `default` for the schedule would make the project's choice depend on a file name, and leave no room for another schedule or for a plain list.

## Decision

1. **A new content file, the schedule** ([`pixelart-schedule/1`](../format/schedule-v1.md)). `content/schedules/seasons.yaml` is published as `schedules/seasons.json` in the content release, listed in a new optional `schedules` list of the manifest, installed by updates after the playlists, and uploadable over USB and WiFi with the new `schedule` kind. A schedule has a required `fallback` and up to 64 entries, each with a range of days (`from`, `to`, with the parts `year`, `month`, `day` in six accepted sets) and up to 8 playlists. A board stores several schedules and plays one at a time: the one the server choice names, the one the user chose, or the schedule `default` as the board's own rule.
2. **One entry wins, by fixed rules.** For a date, more parts win, then the more important part, then the shorter range; a remaining tie is an error of the build tools, and a board takes the first tied entry in the file. The rules make a specific day (December 25) win over a season (December 1 to January 6), which wins over a month (December), without priorities to write by hand.
3. **Automatic or My choice.** A new setting `play` chooses between `auto`, where the server choice decides, `playlists`, where the board plays the user's own list, the new setting `playlists`, of 1 to 8 playlists played in turn, and `schedule`, where it plays the schedule of the new setting `schedule`. Both the list and the schedule are kept while another mode is active. Automatic is the default.
4. **The old `playlist` setting stays, and means the same to older clients.** A board without a stored `play` derives it: `default` means Automatic, any other playlist means My choice, Playlists with that one, so an upgrade keeps every board's choice and writes nothing. `playlist` reports `default` in Automatic and in My choice, Schedule, and the first of the user's playlists otherwise, and the board keeps its stored key equal to that, so a rollback plays what the user expects. An older client that sets `playlist` sets the mode with it.
5. **A list of playlists, played in turn, with a fallback chain.** The board computes a list (the winning entry's playlists, the schedule's `fallback`, the server's list or the user's list), plays each playlist in full, in order, and starts again. Missing playlists are skipped. For a schedule the chain goes on to `fallback`, then `default`, then every animation, then the "no animations" image; My choice, Playlists goes straight to every animation, as a missing active playlist did before.
6. **Without a usable choice or without the time, the board plays what it played before.** With no server choice, or one that names something the board does not have, the board's own rule plays the schedule `default` if it is stored and valid, else the playlist `default`. Without the time, a schedule plays its `fallback`. The first published schedule has `fallback: [default]`, and the playlist `default` keeps its items, so older boards, the simulator and Automatic outside the seasons play what they play today. A `christmas` playlist holds the Christmas items.
7. **The board chooses again only at events,** and switches between animations. It resolves one date, at boot, when the time becomes known, at local midnight, when a playlist, schedule or play file is stored or deleted, when `timezone` changes and when the play settings change. A new list takes effect when the current animation ends. The board never loops over years; only the build tools check every date for ties, limited to the years the dated entries cover plus one leap year and one common year.
8. **The time when the schedule needs it.** The board asks for the time when the choice uses a schedule, whatever its source, or when a narrow install window needs it, from the new setting `ntp_server` (`pool.ntp.org` by default) every `time_sync_hours` hours (6 by default), which replaces the fixed 12-hour resync. The `timezone` setting gives the local date as it gives the local time of the install window. The project owner approved the extra contact with the time server on 2026-10-28, and the privacy texts of the web app say when the board makes it.
9. **The protocol grows only by addition.** The `schedule` kind, `info.formats.schedule` and `info.limits.schedule`, the five new settings, the `play` kind, `info.formats.play` and `info.limits.play`, `status.play` and the `schedules` and `play` counts of `delete_all` are new; nothing changes for an older client. A web app offers the new choices only to a board that reports `formats.schedule` (and the play file only to one that reports `formats.play`), and falls back to "Active playlist" for an older one. The promise that every setting fits in one 1,024-byte `settings_set` is dropped: a client sends only the settings it changes.
10. **One resolver, two implementations, shared cases.** The firmware and the simulator use one C++ resolver; the web app has a TypeScript twin for its "now" and "next" view. Both pass the same hand-computed conformance rows.
11. **The server choice is a content file, the play file.** `content/play.yaml` ([`pixelart-play/1`](../format/play-v1.md)) is built as `play/default.json`, with `default: {"schedule": "<id>"}` or `{"playlists": ["<id>", ...]}`. It is a file of the board like the schedules, with its own folder `/play`, its own protocol kind `play`, and its own optional `play` list in the manifest. The board's server choice is the `default` of a valid `/play/default.json`; a missing or invalid file is no choice, and `status.play.server_choice` reports it. The manifest still never changes a setting. The first release sets `default: { schedule: seasons }`.
12. **The play file reaches a board like every other file.** Updates install it after the schedules, with the server winning and only while `update_animations` is on; the web app and `pixelart.py` upload it over USB with the other files; the content image written by `make data` holds it, so a freshly flashed board has the choice from its first boot. `delete_all` removes it with the other files.
13. **No choice, or a missing target, falls back to the old behavior.** A board with no server choice (a board with no valid play file, such as one with an older content release or a wiped one), a server choice or a user's schedule that names something missing, and a server list with no playable playlist, all play the schedule `default` if stored, else the playlist `default`, else every animation, as the boards before did. The playlist `default` stays for older boards and as the last fallback: the manifest adds to the convention and never replaces it.

## Alternatives considered

- **Changing `playlist` from the server.** The update could rewrite the setting, but a manifest must never change a setting ([WiFi and updates](../board/wifi-and-updates-v1.md#security)), and the user's own choice would be lost twice a year.
- **Dates inside the playlist file.** Each playlist could carry its season, but the board would have to read every playlist to choose, a playlist would carry two concerns, and `pixelart-playlist/1` would need a new version.
- **Explicit priorities on entries.** A number per entry decides any overlap, but every new entry means renumbering, and two equal numbers are a tie anyway. The fixed rules make the common cases, a day inside a season inside a month, work without one.
- **Several schedules played at once.** Only one plays at a time. The user chooses at most one, and the server names at most one, so no rule has to merge two schedules.
- **A fixed schedule ID for the server's choice.** The board would play the schedule `default` in Automatic, and the project could not name another schedule or a plain list. The play file replaces it, and the schedule `default` stays only as the board's own rule for a board with no choice.
- **Making the server choice a setting.** The manifest would write a setting, which it must never do, and the user's own choice would share a key with the project's.
- **A `default` field in the manifest, stored in the settings memory.** The first design had the board copy the manifest's `default` into its settings memory at each check, and a command, `server_choice_set`, for boards filled over USB. That needed a hidden stored value outside `settings_get`, a rule for what a failed or skipped check does to it, a rule for what `delete_all` does to it, a new command for offline boards, and a different path for the same information on each way a board gets its content. A file needs none of this: updates, USB uploads, the content image, `list`, `get` and `delete_all` already handle files, the board reads the choice from the file it stores, and a copy of the release served anywhere carries it with its files. Older boards ignore the `play` list as they ignore every field they do not know.
- **A new protocol version.** Protocol 2 would let `playlist` change meaning, but every older client would stop working with a new board, and every older board with a new client.
- **Asking for the time always.** Simpler, but a board in My choice, Playlists with no narrow window would contact a server it does not need.

## Consequences

- The project chooses the season for every board in Automatic with a content release, and a user who wants another choice picks My choice in the web app: a list of playlists, or one of the schedules on the board.
- Older boards ignore the manifest's `schedules` and `play` lists and keep playing their `playlist`; older web apps and tools keep setting it, and on a new board their `default` means Automatic.
- A board whose choice uses a schedule contacts the time server, which it did before only for a narrow install window.
- A board filled from the content image or over USB has the play file with its other files, so it follows the project's choice from its first boot. A board without a valid play file plays the playlist `default` all year.
- A check against a manifest without a `play` list changes nothing: the play file stays on the board, and a user who points `animation_source` at an older copy of the content keeps the project's last choice. Deleting the file, or `delete_all`, clears it.
- The settings memory holds five more settings, and the longest `settings_set` no longer fits in one line, so a client that sends every setting at once must send them in parts.
- The board does a little more work at a switch: it reads at most two schedules (the named one, then `default`), one at a time, and the playlists of the list, at most one date over 64 entries, between two animations. Its time, the frame timing and the loop task's stack are measured on a board before and after the change.
- The conformance suite gains schedule files, winner and resolver rows, and protocol cases with a local date and with a play file.
