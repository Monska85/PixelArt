# 5. WiFi, updates from GitHub Pages and the protocol over the network

Date: 2026-10-23

Status: accepted

Note: the LED timing of the Context was checked by eye after this record, on an ESP32-C3 with a 16x16 panel. The animations play cleanly on WiFi; animation updates, which write files to flash, show a few brief glitches, judged acceptable; the firmware installation's icon and progress bar show cleanly. See [WiFi and updates](../board/wifi-and-updates-v1.md#tasks-and-memory).

## Context

A board is managed over USB only: the web app and `tools/pixelart.py` speak the [command protocol](../protocol/protocol-v1.md) over the serial port, and new firmware or animations reach the board only when someone plugs it in. Phase 4 lets a board on WiFi keep its animations and firmware up to date by itself, under the user's control, and lets the web app reach it over the network. The [WiFi and updates specification](../board/wifi-and-updates-v1.md) describes what the board does.

Some constraints shape the solution, several of them measured on an ESP32-C3 SuperMini with throwaway prototype firmware on 2026-10-23:

- **Firmware size.** The firmware is built with Arduino-ESP32 2.0.17, the last version the official PlatformIO platform shipped until PlatformIO 8.0.0 (2026-10-19) added Arduino-ESP32 3.3.12, the latest stable release, on ESP-IDF 5.5.5. On 3.3.12 the current firmware takes 667 KB, against 400 KB on 2.0.17. WiFi, an HTTPS client, an HTTPS server and mDNS add about 960 KB, so the phase 4 firmware needs about 1.7 MB. Each firmware slot of the current flash layout holds 1.25 MB.
- **Memory.** With WiFi connected, about 143 KB of heap is free. One HTTPS download from GitHub Pages with the certificate bundle used up to 67 KB more at its peak, and no memory leaked over repeated downloads. Loading an animation can take up to 64 KiB plus its parse.
- **One loop.** The board plays animations and answers protocol requests on one task, the Arduino loop task, whose stack is 8 KB. A TLS handshake takes about one second and a download several, so network work cannot run there without stopping the animation.
- **LED timing.** With WiFi idle and during an HTTPS download, the frames kept their schedule and `show()` took 11 ms, as with WiFi off. On Arduino-ESP32 3.3.12 the RMT driver and its interrupt handler run from internal RAM, so flash writes should not stop a frame on its way to the LEDs. This could not be checked by eye yet, since no panel was connected.
- **Networks.** On a network with client isolation and broadcast filtering the board joined the access point and never received a DHCP answer, while other devices did; on an ordinary network it got an address at once. The board connected at every transmit power from 8.5 to 20 dBm. Some ESP32-C3 SuperMini boards are reported to connect only at low power because of their antenna.
- **Browsers.** The web app runs on `https://monska85.github.io`. A board on the local network has no publicly trusted certificate, and browsers block a secure page from opening an insecure connection (mixed content). Chrome lets a public page reach a device on the local network after a permission prompt (Local Network Access); Firefox and Safari are expected to block the insecure connection, which the browser test of decision 11 confirms.
- **Rollback.** The Arduino-ESP32 bootloader is built with app rollback enabled, and the core lets the firmware confirm itself after a health check instead of before `setup()`.

## Decision

1. **Arduino-ESP32 3.3.12 with PlatformIO `espressif32` 8.0.0,** the first step of phase 4. The simulator's frames stay byte-identical and the three boards keep building.
2. **A new flash layout, set before the first release:** two firmware slots of 1.5 MiB (`0x180000`) each and a file system of 960 KiB (`0xF0000`) for animations and playlists. The coredump partition goes, since nothing reads it. The 30 animations of the repository take 54 KB. The firmware fits the slot because it is built with `-Os`, which the PlatformIO platform does not pass on its own, and with Espressif's common certificate bundle of 43 roots instead of the full one of 150. Link-time optimization and another platform were left out. After the first release a layout change means a USB reflash that erases every user's animations.
3. **A network task next to the loop task.** WiFi, HTTPS downloads and the network transport run on their own FreeRTOS task with its own stack. Everything that touches the engine, the player, the settings or the stored files stays on the loop task, as today: the network task only moves bytes, writes a download to a temporary file, and hands work to the loop task through a queue. Only one large allocation (a TLS connection or an animation parse) happens at a time.
4. **WiFi setup with Improv Serial** on the same USB port as the protocol: the line reader hands Improv frames to the Improv handler and keeps `@PR` lines as they are. The web app and ESP Web Tools use it. Credentials stay in NVS.
5. **A transmit power setting,** `auto` by default: full power, falling back to 8.5 dBm when the connection fails twice. Fixed values from 8.5 to 19.5 dBm are allowed, and a fixed value that fails three times falls back to 8.5 dBm until the next restart, so a wrong value never takes the board off the network.
6. **Updates from the release manifest.** The board reads the [release manifest](../format/manifest-v1.md) over HTTPS with Espressif's common certificate bundle, on a schedule (every 6 hours by default) and on request. The firmware comes only from the project's manifest, built into the firmware, on the stable releases. The manifest address is the site address fixed at build time (the project's own for local builds, the fork's GitHub Pages address in GitHub Actions, or `PIXELART_SITE_URL`), so a fork needs no code change; the web app's default animation source is likewise the `manifest.json` next to the page it is served from. Animations and playlists come from a manifest URL in the settings, the project's by default.
7. **Three update modes, one switch each for firmware and animations.** `off` never checks, `notify` checks and reports, `automatic` (the default) installs within an install window, the whole day by default. Only a request through the protocol changes these settings. The first draft made `notify` the default; the project owner changed the default to `automatic`, so a new board, and a board after a settings reset, installs updates by itself. The install window, the rollback, the skip list and the refusal of downgrades stay as decided, which is what makes that default safe.
8. **The server wins for animations.** With animation updates on, every animation and playlist of the manifest is installed, replacing a stored file with the same ID, and added when missing. Stored files the manifest does not list are never touched.
9. **A/B firmware updates with rollback always on.** The new firmware goes to the inactive slot, is checked against the manifest's size and SHA-256, and boots on trial. It confirms itself once it has started and shown a frame; otherwise the bootloader starts the previous firmware again. A version that rolled back is not installed automatically again. Downgrades are never installed over the network. Installing any firmware over USB always works.
10. **The protocol over WiFi** on a WebSocket served by the board, one protocol line per message, one client at a time, accepted only from the project's site, local pages and pages on private networks (private IPv4 addresses and `.local` names). Network login is off by default, so anyone on the network can manage the board, as on most home devices. With network login on, a client proves it knows the board's token with a challenge and an HMAC, and the token never crosses the network. A refused origin is closed with status 1008 after the handshake, not answered with a 403, because the board's HTTP server answers the handshake before the board's code runs.
11. **A token made by the board, and plain WebSockets first.** At first start the board creates a random 16-character token, readable and renewable over USB only. A reset of every setting also forgets the WiFi network and makes a new token, so it works over USB only. The WebSocket is plain `ws://`, which Chrome allows after its local network prompt. Once the Pages site is live, Chrome and Firefox are tested against it; if browsers need TLS, a later change adds a self-signed certificate made by the board, valid for 10 years and renewable over USB, as the specification describes.
12. **The matrix shows a download icon with a progress bar** while firmware installs. Animation updates do not interrupt the animation.
13. **Small additions after the first review.** `status` reports the name of the stored network (`wifi.ssid`), never the password, so a client can tell which network the board joined; over WiFi it follows the rule of every command, so with network login on only a logged in client gets it. A manifest that answers 404 fails the check with `http_error` and the detail `update.last_detail` `no_release`, because until the first release the Pages site does not exist and the plain error says nothing a user can act on; a file that answers 404 stays a plain `http_error`. The board answers `GET /` with a small inert page that links to the web app, and any other unknown path with a plain 404, instead of the HTTP server's default message.

The work is delivered in five steps: the new framework and flash layout, WiFi, animation updates, firmware updates, the protocol over WiFi.

## Alternatives considered

- **Staying on Arduino-ESP32 2.0.17.** The firmware would be smaller, but 2.0.17 receives no fixes, lacks newer TLS and update code, and still needs a larger slot once WiFi and TLS are added.
- **Keeping the 1.25 MB slots.** The phase 4 firmware does not fit. Dropping the HTTPS server and mDNS saves about 80 KB, not enough.
- **One firmware slot and a factory image.** More room for animations, but an update would overwrite the running firmware, and a failed update would leave the board without one. Rollback needs two slots.
- **Updating the file system as one LittleFS image.** One download instead of many, but a failure halfway erases every animation, and the user's own files would be lost on every update.
- **Running the updater on the loop task.** No locks at all, but the animation would stop for every TLS handshake and download.
- **Our own WiFi command in the protocol instead of Improv.** Slightly simpler, but ESP Web Tools would lose its ready-made WiFi form after an install.
- **A web app served by the board.** It would avoid mixed content in every browser. Rejected for now: it costs flash, RAM, an HTTP server and a second copy of the app to keep in step with the firmware. It stays in the backlog in case the browser tests fail.
- **Signed firmware (secure boot or signatures checked by the updater).** It would protect against a compromised release account. The firmware comes only from the project's releases over HTTPS and is checked against the manifest's SHA-256, and whoever controls the account can publish releases anyway. Kept in the backlog.
- **A beta channel.** It needs pre-releases and a second manifest. Animations and firmware are tested locally with updates off instead.
- **Authentication always on.** Safer on shared networks, but every user would have to copy a token before using the board over WiFi. It is one switch away.
- **Keeping the user's edited or deleted animations out of updates.** It needs a record of what each update installed. The project chose the simpler rule that the server wins; turning animation updates off keeps local changes.

## Consequences

- The firmware grows from 400 KB to about 1.37 MB on the ESP32-C3 (1.76 MB before `-Os` and the common bundle), which leaves about 200 KB free in its slot, and the file system shrinks from 1.4 MB to 960 KiB. The release build refuses a firmware that leaves less than 64 KiB free. Boards flashed before the new layout need one USB install from scratch, which erases their animations; no release has been published yet.
- An `https://` animation source must use a certificate that chains up to one of the 43 common roots. The bundle is made again with a pinned procedure when the framework moves to another esp-idf release, and CI checks that the GitHub Pages chain still verifies against it.
- The protocol grows within version 1: new settings, a `status` command, update commands, token commands and authentication, each with conformance cases. The simulator reports the new file system size.
- Network code adds a task with its own stack and a queue to the loop task. The loop task's stack is measured as AGENTS.md requires.
- Anyone on the local network can manage a board until the user turns network login on. The specification and the web app say so next to the switch.
- A rolled back firmware version stays on the board's skip list until a newer release appears. The user can still install it with `force` over the protocol, or by hand over USB.
- With animation updates on, local edits to published animations are overwritten at the next update.
- Boards install updates by themselves inside the install window, which is the whole day by default, as soon as a release is published. A board updated from a firmware whose default was `notify` keeps a mode that was stored and reads `automatic` when none was, as the [specification](../board/wifi-and-updates-v1.md#settings) says; an owner who wants to approve updates sets `notify` or `off`.
- The board needs internet access to GitHub Pages for updates, and NTP only when the install window is narrower than the whole day.
- Networks that filter DHCP for unknown devices keep the board offline; the web app says that the board joined the WiFi but got no address.
