# Web app, version 1

Status: **implemented** by the web app in `web/`.

This document specifies the PixelArt web app: a static site that installs the firmware on a board, shows what the board stores, uploads, downloads and deletes animations, playlists and schedules, changes the board's settings, and edits animations. It needs nothing installed on the computer. Why the web app works this way is recorded in [ADR 0004](../adr/0004-web-app.md).

The web app talks to boards with the [command protocol](../protocol/protocol-v1.md), reads and writes the [animation](../format/pixelart-v1.md), [playlist](../format/playlist-v1.md) and [schedule](../format/schedule-v1.md) formats, and reads the [release manifest](../format/manifest-v1.md).

## Where it runs

- **Address.** GitHub Pages, at `https://monska85.github.io/PixelArt/` for the project (a fork publishes at its own address, see the [board specification](../board/wifi-and-updates-v1.md#site-address)), at the root of the same site as the published firmware and animations. See [Publishing](#publishing).
- **Browsers.** Connecting to a board and installing firmware need Web Serial, which only desktop Chromium browsers have: Chrome, Edge, Opera and others built on Chromium. In other browsers (Firefox, Safari, phones) the app still connects to the simulator and still edits and previews animations; the board and firmware buttons are replaced by a message that names the browsers that work.
- **Development.** `make web-dev` starts the app on `http://localhost:5173` with live reload. `make serve` starts the simulator with the command protocol on `ws://127.0.0.1:8765` (it needs Python with the `websockets` package), so the whole app works without a board; it accepts the app's origins, see [WebSocket](../protocol/protocol-v1.md#websocket-simulator).

The app is a single page with four views, reached from a bar at the top: **Board**, **Library**, **Firmware** and **Editor**. The address keeps the view in its fragment (`#board`, `#library`, `#firmware`, `#editor`), so reloading the page stays on the same view.

## User interface

The app is built from one set of components and a few layout patterns, so every view looks and behaves the same. The components come from shadcn/ui: Radix primitives give the behavior (keyboard, focus, screen readers), Tailwind CSS gives the look, and the component code lives in `web/src/ui/components/`. Icons come from lucide-react. Why: [ADR 0004](../adr/0004-web-app.md), decision 9. A view never draws its own variant of a component or a pattern below.

The details the build settled:

- **Menus of choices** (the animation of a playlist item, the active playlist, the angles of a sprite) use the browser's own select control, styled like the other fields: it is the most accessible choice and adds nothing to the download.
- **Side panels** are Radix Dialog without its modal part, so the list next to them stays usable (a wide panel below 1,024 px is the one exception, see below). From 1,024 px wide they sit in a column to the right of the list; below that they are fixed to the bottom of the screen, with their title and their buttons staying in view. Escape and the close button close them.
- **Wide panels** are side panels for editing that needs room: the playlist editor. From 1,024 px wide a wide panel spans the whole content width above the list that opened it, and the list stays usable below it; below that it fills the screen, with its title and its buttons staying in view, and it is modal: focus stays in it and the page behind it is hidden from screen readers, since that page cannot be seen. Whether a wide panel is modal is decided when it opens and kept while it is open, so resizing the window or turning a tablet never rebuilds it or hides a dialog opened from it. The cost is a rare one: a wide panel opened on a phone stays modal when the window widens, so the page next to it can be used again once the panel is closed.
- **Theme:** the page carries the theme in `data-theme` on the root element. A small script in the head (no inline script) sets it from the remembered choice or the operating system before the first paint; the app keeps it in step with the operating system while the choice is System.
- **Disabled actions** keep their style and their contrast, and a tooltip on them says why they are disabled.
- **Menus:** a menu is used only for two or more actions; a single action is a direct icon button with a tooltip.

### App shell

- **Top bar:** the name PixelArt, the navigation (Board, Library, Firmware, Editor) as one tab-style bar with the current view marked, the connection chip and the theme control. Below 640 px wide the navigation becomes a menu button that shows the current view.
- **Connection chip:** a dot and a word for the state (Connected, Connecting, Lost, Not connected; never color alone), and when connected the board and its firmware. It opens a panel with the details (board, firmware, storage), **Disconnect**, **Connect board** and the simulator address with **Connect simulator**. The connect controls are not shown on the page while a board is connected.
- **Footer:** one quiet line at the bottom of every view, always shown: "Runs entirely in your browser. Your animations, settings and WiFi details go only to your board. The board itself contacts only its update source and its time server.", followed by **Privacy**, a link to the [Privacy view](#privacy), and **Source**, a link to the repository that opens in a new tab.
- **Not connected:** the Board view shows a connect card with **Connect board** (primary) and, folded under "Use the simulator", the address and **Connect simulator**. Library, Firmware and Editor work without a board and say in place what needs one.
- **Lost connection:** one alert under the top bar, "Connection lost. Reconnect to continue.", with **Reconnect**. Actions that need the board are disabled and their tooltip says why.
- **Theme control:** three states, **System** (the default), **Dark** and **Light**. System follows the operating system and changes live when the operating system switches. The control is one icon button, not a menu: a click moves on from System to Dark, from Dark to Light and from Light back to System. The icon shows the current state (a monitor, a moon or a sun), the tooltip names the current state and the next one ("Theme: System. Click for Dark."), and the accessible name carries the same text, so a screen reader announces the state. Enter and Space work as they do on any button. The choice is remembered in the browser; when the browser refuses to store it, the app stays on System. Text and controls meet the WCAG AA contrast ratios in both themes.

### Page pattern

Every view starts with the same page header: the title (`h2`), one line saying what the view is for, and on the right the view's single primary action, its secondary actions, and a **More** menu for the rest. On a phone the secondary actions move into **More**. Content follows in cards with one shared style. The Board view is the one exception to the actions on the right: its file actions are in the header of its Files card, see [Files](#files).

### List pattern

Board and Library show their files the same way:

- **Tabs** **Animations** and **Playlists**, and on the Board **Schedules** for a firmware that knows them, with counts, as a tab component (not buttons); the tab label is the only heading, the card below repeats nothing.
- **A table** that fills its card: the name with the ID under it in monospace (cut with an ellipsis, whole in a tooltip), then the view's own columns (Board: version and size; Library: version and the state on this board), all vertically centered on one line.
- **Row actions** at the right end, aligned with the cells: up to three icon buttons with a tooltip and an accessible name, then, when there are two actions or more to fold away, a **More** menu (⋯). Destructive items are last in the menu, in the danger color. A menu is used only for two or more actions; a single action is a direct icon button with a tooltip, never a menu of one.
- **Install on the row:** a file listed as not on the board (or different from the board's copy) has a visible **Install** icon button on its row, never hidden in a menu. A playlist's Install brings its animations through the shared upload queue.
- **Preview opens in a side panel** (from the right on a wide screen, from the bottom on a phone), next to the list that opened it, and **the playlist editor in a wide panel** (above the list on a wide screen, the whole screen below 1,024 px), never at the end of the page.
- **Below 640 px** each row becomes two lines (name and ID, then the columns as text) with the actions on the right; the page never scrolls sideways.
- **Empty list:** only for a list the app has read and found empty: a title ("No animations on this board"), one sentence, and the actions that fill it (animations: **Upload files** and **Install from the Library**; playlists: **New playlist** and **Install from the Library**).
- **List not read yet:** while the first read after connecting is under way, a loading line ("Reading the files from the board...") and no counts, never the empty list. In the Library, the state column stays blank and a line says "Reading the board...".
- **List that could not be read:** the notice "Could not read the files from the board." with **Retry**, which reads the lists again; the tab shows no count. The Library shows the same notice above its tables, and its state column stays blank rather than saying "Not on the board". A failed read is reported once, as an error of the view that sees it first, not again when another view opens.
- **List read again after a change:** the rows stay while the new read is under way.

### Dialog pattern

Every confirmation is a dialog. The title is a short question with the verb ("Delete ball?"); the text says what changes and names the files. Buttons are at the bottom right: the safe action on the left (**Cancel**, or a precise label such as **Keep editing**), the action on the right with a verb label (**Delete**, **Replace**, **Discard and open**, **Use this ID**). Only destructive actions are red. Escape cancels; focus starts on the safe action for destructive dialogs, and goes back to the control that opened the dialog when it closes. On a phone the dialog fills the width at the bottom of the screen.

### Feedback pattern

- **Progress:** an action that takes time shows a spinner in its button, and uploads, installs and the wipe show one activity panel under the page header (file N of M, a progress bar, **Cancel**). It is the same panel in every view.
- **Results:** a toast for the outcome of an action ("Uploaded 3 animations"), which also announces it to screen readers.
- **Errors:** one alert component (icon, title, text, and the diagnostics table when there are diagnostics), shown next to what failed and kept until the user acts. The diagnostics table follows the width of the box it is in: below 36 rem (a phone, or the editor's side column) the code and the place go in front of the message instead of in columns of their own. Errors are never red text on a colored background.

### Wording and formats

- Sentence case for every label, title, badge and menu item.
- Verbs: **Upload** sends files from the computer to the board, **Install** sends published files from the Library, **Download** saves to the computer, **Open** loads into the editor. "Save" is not used for these.
- Nouns: "animation" and "playlist"; "file" only when the kind is not known.
- Sizes: bytes below 1,024 (`845 B`), then KB and MB with one decimal (`2.9 KB`, `1.4 MB`), base 1,024, everywhere.
- States are words with an icon (On the board, Same, Different, Active), never color alone.

### Forms

Labels above fields; a hint in muted text under the field; an error replaces the hint in the danger color and is linked with `aria-describedby`. Filled-in values look like values, placeholders only show examples. Numbers use number fields or sliders with the value shown next to them.

### Accessibility, spacing and size

- Everything works with the keyboard and shows a visible focus ring; `prefers-reduced-motion` turns off animations.
- One spacing scale (multiples of 4 px), one card style, `h2` for the page, `h3` for cards; monospace only for IDs, codes and YAML.
- The content is at most 72 rem wide and centered, with a 16 px margin on phones.
- **Size budget:** the JavaScript the page loads at start (the entry chunk and the chunks it imports, each gzipped, 1 KB being 1,000 bytes) stays within 192 KB; `npm run size` checks it and CI fails the build above it. Everything else loads on demand: the Library, Firmware, Editor and Privacy views, the WiFi, Updates and Network access cards of the Board view (loaded together when a board connects, since they show only for a connected board), the playlist editor, the YAML reader, the editor's document store (which brings the stored draft back right after the first paint) and ESP Web Tools.

## Connection

The connection chip of the [app shell](#user-interface) is always visible. It shows the state (Not connected, Connecting, Connected, Lost) and, when connected, the board and its firmware version. Its panel shows the details, including the storage used and free, and holds the connect and disconnect controls.

### Transports

- **Board (USB).** "Connect board" asks the browser for a serial port (`navigator.serial.requestPort()`), then opens it at 115,200 baud with `bufferSize` 8,192 and keeps DTR and RTS low, so opening the port does not reset the board. Incoming bytes arrive in arbitrary pieces; a stream transform splits them into lines at `\n` and drops a `\r` before it. Lines longer than 16 KiB are dropped up to the next newline.
- **Simulator (WebSocket).** "Connect simulator" opens a WebSocket to the address in the field next to the button, `ws://127.0.0.1:8765` by default. The app accepts only `ws://` addresses on `127.0.0.1` or `localhost`; any other address gets an error at once. The address is remembered in the browser. Each text message is one line. Chrome may ask the user to allow the page to reach devices on the local network the first time a page from the internet connects to `127.0.0.1`; the app says so next to the button.

- **Board (WiFi).** "Connect over WiFi" opens a WebSocket to the board's address, `ws://<address>/ws`. The address is a field in the connect card and in the connection panel, **Board address**: the board's hostname (`pixelart-XXXX.local`) or its IPv4 address, with an optional port, typed by the user or remembered. The app accepts any host name made of letters, digits, hyphens and dots, so a name the user's router or network gives the board works as well as the board's own, and it does not check that the host is a board: the address is the user's own choice, and the app sends the protocol requests and the chosen files to the address entered. The app remembers the address of the last WiFi connection and, after a USB connection, the hostname the board reported with `status` (as `pixelart-XXXX.local`). It accepts a leading `ws://` and a trailing `/ws`, writes the name in lowercase, and refuses anything else (user information, another path, an IPv6 address, a leading zero in a number, a port outside 1 to 65535) at once, with the way to write an address. The field's hint says that Chrome asks to allow the page to reach devices on the local network the first time. A connection that fails says it could not connect, and that Connecting over WiFi is expected to work in Chromium browsers (Chrome, Edge, Opera) while Firefox and Safari are expected not to let a page from the internet reach a board; a browser without `navigator.userAgentData` gets that note above the field from the start. The board serves one client at a time, so the app tries 6 times before it gives up, and waits longer after each refusal: 200, 400, 800, 1,600 and then 3,200 milliseconds, about 6.2 seconds in all. A second tab, or a reload while the board still holds the old connection, therefore sends the board a few connections, never a burst. The board pings the holder at the first refusal and closes a holder that sends nothing back for 3 seconds at the next refusal after that, so a reload whose old connection the board never saw closed gets in with the last try, about 6.2 seconds after the first. The simulator's WebSocket is tried the same way. How the board serves this WebSocket is specified in [WiFi and updates](../board/wifi-and-updates-v1.md#protocol-over-wifi); the board currently serves `ws://`.

  **Login.** The protocol client logs in when a request is answered `unauthorized` (network login is on), and then sends the request again: it asks for `auth_challenge`, and answers with `auth` and the HMAC-SHA256 of the nonce under the token, computed with Web Crypto. `info` needs no login, so the connection is made first. The token is asked in a dialog, **Log in to the board**, with a masked field (16 characters, `a-z` and `0-9`), once per board: the browser remembers it in its storage under the address used to connect, and the next connection logs in without a question. The token is never sent, shown or logged by the app, only the HMAC. When the user cancels the dialog, or the board answers `unauthorized` to the login (the token is forgotten then; another failure keeps it), the connection ends with a message that says how to try again; the board closes a connection after 3 wrong answers.

Both transports deliver lines to the same protocol client. Lines that do not start with `@PR ` are ignored, as are lines with a bad CRC. Board lines with an `event` field and no `seq` are ignored, since protocol 1 defines no events.

Only one program can open a serial port. If the port is busy (another browser tab, the serial monitor or `tools/pixelart.py` holds it), the browser refuses to open it, and the app says to close the other program, followed by what the browser said in brackets (for example "NetworkError: Failed to open serial port."), so a failure of another kind can be told apart.

When the page itself still holds the port open ("InvalidStateError"), the app first closes the connection of this page that holds it, releasing its streams, because a port cannot close while a stream is locked. It then waits for a close still under way (at most one second), closes the port if it is still open, and opens it once more. Only a second failure is reported.

Any failure after the port opened (no streams, a board that does not answer the handshake, a cancelled connection) closes the port again, and closing always reaches the port: the reader is cancelled and released, the pipe settles, the writer is aborted and released, and then the port closes, trying a second time if the browser refused the first. Each stream gets at most one second to finish, because a device that went away (unplugged, or reset on USB) can leave a write or a read pending forever, and a port left open stays busy for every later attempt until the browser is restarted. After a lost connection, **Reconnect** closes the old port before it asks for one again.

### Handshake and versions

Right after the transport opens, the client sends `info` and waits for the reply before anything else. It retries as described under [Requests](#requests), so a board that is still starting has time to answer.

When the port opened over USB but the board gives no valid reply after the tries (a board that never reads its USB input, or one that sends only lines that are not the protocol, such as the log of an old sketch), the app shows "This board did not answer as a PixelArt board. Its firmware may be old or missing: install the firmware from the Firmware view." and offers the Firmware view. The port is released, so Connect board opens it again at once. The message for a port the browser cannot open (above) and the messages of the simulator and of WiFi connections do not change.

- `info.protocol` must be `1`. Otherwise the app shows "This board speaks protocol N, which this web app does not know" and offers the Firmware view; it sends nothing else.
- `info.formats.animation` must contain `pixelart/1` and `info.formats.playlist` must contain `pixelart-playlist/1`. Otherwise uploads are disabled and the app offers a firmware update.
- `info.limits` gives the line length, chunk size, page size and file limits. The client uses these values, never the ones of the protocol document.
- `info.boot_id` is remembered. When a later `info` reports another value, the board has restarted: any upload in progress is gone, and the app reloads the file list and the settings.

### Requests

The client follows the rules of the protocol and does what `tools/pixelart.py` does:

- One request in flight. The next one is sent only after the reply or after the client gave up.
- The first `seq` is random, then it increases by one for each new request, wrapping after 4,294,967,295.
- Requests are written as `@PR <crc> <json>` with the CRC-32 of the JSON bytes, and the JSON escapes every character outside ASCII (`\uXXXX`), so a line's length in bytes equals its length in characters.
- The client waits 2 seconds for a reply, 10 seconds for `put_end` and `delete_all`, and sends the same request again with the same `seq`, up to 5 tries in all.
- A write the link has not taken yet is never written a second time. A try that times out while its write is still pending waits for a reply again without writing, so a board that never reads its input cannot hold a request past its 5 tries.
- A `bad_frame` reply makes the client send the request again at once, as one of the 5 tries.
- A reply whose `seq` is not the request in flight is discarded.
- After 5 tries without a reply the connection state becomes "lost". The user can reconnect; the app then sends `put_abort` if an upload was in progress.

The client never sends a path, only `kind` and `id`.

## Board view

Shown when a board or the simulator is connected.

### Files

The files are in the first card of the view, **Files**, above Storage, Settings, WiFi, Updates and Network access, so every card is within reach without scrolling past the long tables of files. The card always shows its title, the actions below and a one-line summary, and holds the lists under a toggle button. Two lists, animations and playlists, and a third, schedules, on a board whose `info` reports `formats.schedule`, read with `list` page by page until `more` is `false`. A board whose firmware is older than schedules is never asked for the `schedule` kind: it stores none, and its view has the two lists of before. They follow the [list pattern](#list-pattern): the tabs of a tab component, **Animations**, **Playlists** and **Schedules**, each with its number of files, and a table that fills the card. The tabs follow the WAI-ARIA tabs pattern: Left and Right arrows move between them and wrap around, Home and End jump to the first and the last, and focus follows the selected tab. The Animations tab is shown first, and the other list keeps its state (an open preview) while it is hidden.

Each row shows the ID, the name, the version (animations) and the size (written on one line, for example `1,234 B`), then the actions, as described under [User interface](#user-interface):

- **Preview** (icon button, animations): the app downloads the file, loads it with its own engine and plays it in a 16x16 preview with play, pause and step.
- **Edit** (icon button): opens the file in the Editor (animations) or in the playlist editor (playlists). The Editor then offers a way back to the Board view, see [Opening a document](#opening-a-document). Schedules have no editor: the Settings card shows the schedule the board plays, read only.
- **More** menu: **Download JSON** saves the file as stored (`<id>.json`); **Download YAML** saves it converted to YAML (`<id>.yaml`); **Delete**, after a confirmation that names the file. Deleting the active playlist shows an extra line: on a firmware older than schedules, that the board will then play every animation; on one that knows them, where the active playlist is the one the board plays now, that the board will skip it and play every animation when no other playlist of its list can play. Deleting the schedule `default` while Automatic is chosen says that the board will then play the playlist `default`.

The card's header has the actions: **Upload files** (primary) and **Upload folder**, and a **More** menu with **New playlist**, **Refresh** and **Delete everything** (see [Delete everything](#delete-everything)), built as the actions of the [page pattern](#page-pattern) are (below 640 px **Upload folder** moves into **More**). The Board page header keeps only its title and description.

**Summary.** One line, always shown. On a firmware that knows schedules it counts the schedules too and names the What to play choice and the playlist the board says it plays (`status.play.playing`): "41 animations, 3 playlists, 1 schedule, Automatic: playing Halloween", "My choice, playlists: playing Christmas" or "My choice, schedule: playing Christmas". A board that plays no playlist reads "Automatic: every animation plays", and the line names the choice alone before the first status and while the status still reports the other choice. On a firmware older than schedules it names the active playlist: "41 animations, 2 playlists, active playlist: Christmas"; a setting that names a playlist that is not stored reads "active playlist: ID (not stored)", and an empty setting reads "no active playlist: every animation plays". A playlist is shown by its name, or by its ID when it has none. Without the settings the line stops after the counts. While a list is being read it says "Reading the files from the board...", and when a list could not be read "Could not read the files from the board.". The line wraps inside the card, even a name of 64 characters with no space to break at, so the card never grows wider than the screen; the missing-animations warning wraps the same way.

**Missing animations.** When at least one stored playlist misses animations, a warning with an icon and words stays visible under the summary, also while the section is closed: "2 playlists are missing animations: christmas, halloween." (the IDs, at most 10, then "and N more"), with a **Show playlists** button that opens the section, selects the Playlists tab and moves the focus to the tab. See [Missing animations](#missing-animations).

**Toggle.** A button in the card reads **Show all files** when the section is closed and **Hide files** when it is open, with a chevron icon that assistive technology does not read, `aria-expanded` and `aria-controls` pointing at the element that holds the tabs. The section is closed by default. The tabs stay mounted while it is closed (the element is hidden), so the selected tab, an open preview and the dialogs keep their state. The user's choice with the button is kept in `localStorage` under `pixelart.boardFiles` (`open` or `closed`; any other value, or storage that is blocked, reads as closed), so it holds after navigation and reload, per browser.

**Automatic opening.** The section opens by itself when the user needs the list: when a playlist editor opens (Edit, New playlist, or a confirmed switch), when a preview opens, when an upload through the Board view's queue (pickers, drop, Install missing) ends with at least one file uploaded (not when nothing was sent, all failed, or the user cancelled), and with **Show playlists**. An automatic opening is not stored: only the toggle writes `pixelart.boardFiles`, so a moment's need never undoes the choice to keep the list closed. It lasts until the user hides the section or leaves the view; a reload or a return to the view follows the stored choice.

A download reads the file with `get` in chunks of `info.limits.chunk` bytes and compares the SHA-256 of what it read with the one `list` reported. When they differ (the file changed during the download), it reads the file again once, then reports the error.

A file whose name or version the board could not read (the board leaves them out of `list`) is listed with its ID only, and can still be downloaded and deleted.

The play file has no tab: it is one small file of at most 1 KiB that the site publishes and the board's updates and the USB install keep, so the app neither lists it, counts it in the Files summary or the Storage card, nor lets the user pick, download or delete it one by one. It is installed with the site content, deleted by **Delete everything**, and its effect shows in Automatic (the board's `status.play`). The Schedules tab, when it is empty, says that a schedule chooses the playlists the board plays in each season, that the published one comes with **Install all** in the Library, with the update over WiFi (**Install animations**, when **Animation updates** is on) and with **Install from scratch**, and that the user's own is uploaded with **Upload files**. A schedule row shows **Active** next to the schedule the board plays from now (`status.play.schedule`): the one the site chose, the one of My choice, or the board's own rule. Deleting that schedule says whose choice it is and what the board plays instead ("The site chose this schedule for Automatic: the board will then play the schedule default.", "My choice plays this schedule: ...", "Automatic plays this schedule: ...").

### Upload

**Upload files** accepts one or more `.json`, `.yaml` or `.yml` files, picked or dropped on the view. **Upload folder** takes every such file in a folder the user picks (the browser's folder picker), subfolders included; files with another extension are ignored without a message. All of them go through the [upload queue](#upload-queue), also one single file. For each file:

1. **ID.** The file name without its extension, lower-cased. When it does not follow the ID rule, the app asks for one, with the name as a suggestion.
2. **Kind.** From the document's `format` field: `pixelart/1` is an animation, `pixelart-playlist/1` is a playlist, `pixelart-schedule/1` is a schedule. Anything else is refused before upload, with the field's value in the message; the play file (`pixelart-play/1`) is one the site manages, so a file of it that the user picks is refused like any other format. A schedule for a board whose `info` has no `formats.schedule` is refused too, with "This board's firmware does not know schedules, so the file was not uploaded. Update the firmware to use schedules.", and nothing is sent.
3. **Conversion.** A YAML file is converted to JSON as described in [YAML](#yaml). A JSON file is uploaded with its bytes unchanged.
4. **Check.** The app validates the JSON with its own engine. A file with errors is not uploaded: the app shows the diagnostics. Warnings are shown and do not stop the upload.
5. **Replace.** A stored file with the same kind, ID and SHA-256 is skipped, and a toast says the board already has it. When files differ from the stored ones, the queue asks once for all of them, see [Upload queue](#upload-queue). A folder or a selection with two files of the same kind and ID keeps the first and lists the second as left out, unless both are the same file.
6. **Upload,** as described in [Uploads](#uploads). The board validates the file again; its answer is what counts.

The board takes one upload at a time, so the app runs one upload at a time across the Board, Library and Editor views. The lock lives outside the views, so it holds after a change of view, and every view shows the activity panel with a **Cancel** button while an upload runs. Starting another upload while one runs is refused with the code `upload_busy` and the message "Another upload is still running. Wait for it to finish or cancel it." The board holds one upload for USB and WiFi together: while a client on its other connection has one in progress, the board answers `busy`, and the upload fails with the code `busy` and the message "the board is receiving a file over its other connection (USB or WiFi): try again when that upload ends".

### Upload queue

Every upload from the Board view (files, folder, drop), every install from the Library and the editor's **Upload to board** go through one queue, so they all behave the same:

1. **Check.** Every file is converted and validated by the app's engine first. A file with errors, or of another format, is listed with its diagnostics (one alert per file) and left out; the other files go on.
2. **Plan.** The queue reads the board's files with `list` (schedules only on a board that reports `formats.schedule`) and sorts each file into missing, identical (same SHA-256, skipped) or different. When some differ, one dialog lists them with their sizes and asks: **Replace them**, **Keep the board's** (only missing files are sent; the differing ones count as skipped) or **Cancel** (nothing is sent). The dialog starts on **Cancel**.
3. **Playlists bring their animations.** When the queue holds a playlist, it adds every animation the playlist names, enabled or not. It takes each one from the same selection or folder first, then from the published Library (downloaded and checked against the manifest, then compared with the board like any file: identical is skipped, different goes to the dialog above), then it accepts the board's own copy when only the board has it. Animations found nowhere are listed with the playlists that name them, and the dialog **Upload the playlist without all its animations?** offers **Upload the playlist anyway** (the board stores it with an `unknown_animation` warning, as today) or **Cancel**. An animation of the Library that cannot be downloaded or fails the check counts as found nowhere, unless the board stores it: then the board's own copy is used without a question. The dialog names only the playlists that reference each animation.
4. **Space.** Before sending anything, the queue reads `info` again and plays the files in send order against the free space in `info.storage` (total minus used), in blocks of 4,096 bytes. The board needs room for the new file while the old one still exists, so before each file the free space must hold the file's blocks, and a replaced file gives its blocks back only after its replacement is stored. When some file would not fit at its turn, nothing is sent and an alert says how much the files need, how much the board has free and how much more is needed at the tightest point. A board that reports no storage is not checked. When `info` cannot be read, nothing is sent and an alert says the board could not be read.
5. **Send.** Animations go first, then playlists, then schedules, each kind in the order given, one file at a time, so a playlist finds its animations and a schedule its playlists. The queue holds the upload lock from the first file to the last, so no other upload can slip in between two files. The [activity panel](#user-interface) shows the file being sent ("File N of M"), its bytes and a **Cancel** button; **Cancel** sends `put_abort`, counts the file in progress as not attempted and stops.
6. **Stop at the first failure.** The queue stops at the first file the board refuses or that cannot be sent, so a playlist is never sent after one of the animations before it failed. Running the same queue again resumes, because identical files are skipped.
7. **Summary.** A toast says the outcome in one line ("Uploaded 3 animations and 1 playlist", "Installed 3 animations, 1 playlist and 1 schedule", "Installed animation bear", "Upload stopped at ball", "Nothing to upload"). When more than one file is involved, or something failed or was canceled, an alert that stays until dismissed lists what was uploaded (or installed), skipped (the board has the same file, or the board's file was kept), failed (with the board's code and message and its diagnostics) and not attempted. Files that went through with warnings get an alert with the warnings, from the board when it gave some.

The queue is one at a time: while it asks a question or sends, the pickers and the Install buttons are disabled with the reason "Another upload is still running."

### Delete everything

**Delete everything** removes every animation, playlist, schedule and play file on the board with the protocol's `delete_all` command; the firmware stays, and the settings stay unless the user also resets them. It is in the Board view's **More** menu (last, in the danger color) and in a **Reset** card of the Firmware view, with the same dialog in both. The app first reads the lists to count the files (the schedules only on a board that reports `formats.schedule`, the play file only on one that reports `formats.play`); the title and the toast name the schedules and the play file when there are some ("Delete all 12 animations, 1 playlist, 1 schedule and 1 play file from this board?"). The empty-board toast still says "animations, playlists or schedules", since the play file is only counted with them. A board with no files gets a toast ("The board has no animations, playlists or schedules"; in the Firmware view it adds "Check Also reset the settings to put the settings back to their defaults."), unless the settings are to be reset, see below. Otherwise a dialog names what will go (the numbers in these examples are those of a board with 12 animations and 1 playlist; title "Delete all 12 animations and 1 playlist from this board?", text "This cannot be undone. The firmware and the settings stay.") with the button **Delete 13 files**; it starts on **Cancel**. In the Firmware view the button is disabled without a connected board and says so next to it.

The dialog has a checkbox **Also reset the settings**. It is unchecked each time the dialog opens from the Board view. The Firmware view's **Reset** card has the same checkbox, unchecked by default, above its **Delete everything** button, and the dialog opens with its checkbox as the card's is; the card's box is then cleared, so the next Delete everything starts with it off again. On a board with no files and the card's box checked, the dialog asks only for the reset: title "Reset the settings of this board?", text "The board has no animations, playlists or schedules. Every setting goes back to its default (brightness 100, active playlist default, updates, transmit power, network login and the rest), the WiFi network is forgotten and a new token is made.", button **Reset the settings**, and the app sends `delete_all` with `settings: true`, which removes nothing. When it is checked, the text says what goes back to its default ("This cannot be undone. The firmware stays. Every setting goes back to its default (brightness 100, active playlist default, updates, transmit power, network login and the rest), the WiFi network is forgotten and a new token is made."), the button becomes **Delete 13 files and reset the settings**, and the app sends `delete_all` with `settings: true`, so the board removes the files and then resets the settings in one command. While it runs, the activity panel says "Deleting every animation, playlist and schedule and resetting the settings". The toast says so ("Deleted 12 animations and 1 playlist and reset the settings", or "Reset the settings" when there was no file to remove), with a second line "Every setting is back to its default, the WiFi network is forgotten and a new token is made.", and the Board view reads the settings again. Over a WiFi connection the checkbox is disabled, with a tooltip "Resetting the settings needs a USB connection.", because the board reserves the reset for USB (it forgets the WiFi network and makes a new token); the Firmware view's card box is disabled the same way, and a board with no files then only gets the toast. Without the checkbox the request carries no `settings` field, so a firmware older than that field still deletes everything. A firmware that does not know the field answers `bad_request` and deletes nothing: the app says "The firmware of this board cannot reset the settings", that nothing was deleted, and offers the Firmware view, or Delete everything without the reset (for the settings-only reset of a board without files it says that nothing was changed and the firmware needs an update). After a `storage_error`, **Run it again** repeats the same choice, and the alert says so ("Running it again removes the rest and resets the settings.").

While the command runs, the app holds the upload lock, so no upload can start, and the activity panel says "Deleting every animation, playlist and schedule" with a bar that only shows that work goes on and no **Cancel** (the command cannot be stopped). Afterwards the view reads the files again, and a toast says how many were removed. A board whose firmware does not know the command answers `unknown_command`; the app then says the firmware must be updated, with a link to the Firmware view (not shown in the Firmware view itself). When the board answers `storage_error`, the app shows the message, says that the files removed before stay removed, and offers **Run it again**. Any other error is shown as an alert.

The dialog adds a line when the editor holds one of the animations that will go and its only saved copy is that board file, see [Where the work is saved](#where-the-work-is-saved).

### Uploads

An upload follows the protocol's [upload sequence](../protocol/protocol-v1.md#uploads), with the same recovery as `tools/pixelart.py`:

- `put_begin` with kind, ID, size and SHA-256, then `put_chunk` with chunks of `info.limits.chunk` bytes, waiting for each reply, then `put_end`.
- After an acknowledged chunk, the next offset is the reply's `received` when it is larger than the client's own count.
- `bad_offset` resumes from `expected`, at most 5 times per upload.
- `no_upload`, or a changed `boot_id`, restarts the upload from `put_begin` once; a second one fails the upload.
- Any other error sends `put_abort` and reports the error.
- When the connection is lost, the upload fails; after a reconnection the app sends `put_abort`.

### Errors

Every error of the board is shown with its code and the board's message. An `invalid_file` reply also shows the diagnostics as a table: severity, code, place (`where`) and message. The app's own validation uses the same table, so a file looks the same whether the app or the board rejected it. The text of messages and places comes from files and boards and is always shown as plain text.

### Settings

- **Brightness:** a slider from 0 to 255 with the number next to it, sent with `settings_set` when the slider is released. A note says that animations can lower it with their own `brightness`, never raise it.
- **What to play**, on a board whose `info` reports `formats.schedule` (below). A board whose firmware is older than schedules keeps the **Active playlist** menu instead, with the requests of before.
- **Active playlist** (firmware older than schedules): a menu of the stored playlists. Choosing one sends `settings_set {playlist}`. When the setting names a playlist that is not stored (it was deleted), the menu shows it as missing and says the board plays every animation.
- **Time**, on a board that reports `formats.schedule` (below).
- When the active playlist names animations the board does not store, a warning note lists them and offers **Install missing** (see [Missing animations](#missing-animations)). The active playlist is the `playlist` setting on a firmware older than schedules, and the playlist `status.play.playing` names on one that knows them.

The app sends in `settings_set` only the settings the user changes, one change at a time, and the view shows the settings from the reply to `settings_set`, not the values the user asked for. After a change of `play`, `playlists`, `schedule` or `timezone` it reads `status` again, so the cards say what the board chose.

**What to play** is one card with two choices, each with a radio button, its name and one line, side by side from 768 px and in one column below it. The **My choice** pane holds a second radio group, the segmented switch **Playlists** | **Schedule**, which says what My choice plays. Both groups announce a change in a polite live region ("My choice chosen, Playlists.", "Schedule chosen.", "Automatic chosen."), from the board's own state, so a change the board refused is not announced.

The choice and the segment are the `play` setting. The segment shows **Schedule** when `play` is `schedule` and **Playlists** otherwise, but a user can look at the other segment while Automatic plays, which sends nothing. The app sends only what changes:

- Choosing **Automatic** sends `settings_set {play: "auto"}`.
- Choosing **My choice** sends `play` of the segment shown: `schedule` when Schedule is shown, else `playlists`.
- Switching the segment while My choice plays sends `play` alone.
- Picking a schedule sends `schedule`, and `play: "schedule"` with it only when `play` is not `schedule` yet, so choosing a schedule from Automatic also chooses My choice, Schedule.
- A change of the list sends `playlists` alone, which leaves `play` as it is.

**Automatic** ("What the site chose for this board, or the board's own rule when it chose nothing."): the card says what the site chose in the same terms as My choice, from `status.play` alone: `server_choice` is the `default` of the board's valid `/play/default.json`, and `source` says whether the board follows it (`server`) or plays its own rule (`fallback`). The app never guesses from the stored files whether a schedule or a playlist can play, because the board decides that: a stored playlist whose animations are gone, or a stored schedule that is not valid, is not followed. The card says "The site plays the schedule Seasons." and "The site plays the playlists Quiet evening and Christmas." when the board follows the choice; when the site chose nothing, or the board cannot follow the choice, it names what the site asked for and what the board plays instead, from `schedule` and `playlists` ("The site has not chosen what to play, so the board plays the schedule default.", "The site chose the schedule ghost, which the board cannot follow, so it plays the playlist default."). While My choice is in force, `status.play` says nothing about Automatic, so the card only names the choice ("The site chose the schedule Seasons for Automatic.") or says that the site chose nothing and that Automatic plays the board's own rule. While Automatic plays, it then says what the board plays now, from `status.play`: the entry that is on and its playlists ("Now: Halloween is on: the board plays halloween."), the fallback when no entry matches, when the winning entry's playlists cannot play, or while the board does not know the date, and the playlist `default` when the board stores no valid schedule `default`; with "None of them can play, so it plays every animation." when `playing` is null. It then gives the next change of the schedule the board plays from ("Next change: March 16, 2026, the fallback: default.", or "none in the next 12 months."), worked out by the app's engine from today's date in the board's time zone: it looks one day at a time, at most 366 days ahead and never past the year 2999, and never loops over years. **Show the schedule** (a button with `aria-expanded`) shows the schedule read only, as a table with the name, the days and the playlists of each entry in the order of the file, the fallback last, and the entry that wins today marked "Today". The schedule shown is the one `status.play.schedule` names while Automatic plays, and otherwise the one Automatic would play, read from the board with `get` and read again when its SHA-256 in `list` changes; a server choice that is a list of playlists has no schedule to show. A board that stores no schedule gets a line saying so, and the table shows the schedule of the site's own release, the one named by the `default` of the site's play file (downloaded from the site like a Library file and checked by the app's engine), none when that file chooses playlists, which have no schedule to show, and the schedule `default` when the site publishes no play file or one the app cannot read, downloaded from the site like a Library file, if it publishes one. A stored schedule that the app's engine rejects is called not valid.

**My choice, Playlists** ("Your playlists, each one played in full, in turn, or one of the schedules on the board."): the `playlists` setting as an ordered list, numbered, each row with a drag handle, the ID and the name, **Up**, **Down** and **Remove** icon buttons, and an **Add a playlist** menu of the stored playlists that are not in the list, with **Add**. The list is shown and kept while Automatic is chosen, with a line saying so, and can be changed meanwhile. Each change is sent at once: a move with the buttons when it is made, a drag when it is dropped (a drag canceled back to its place sends nothing), a removal and an addition when they are made. The last playlist of the list cannot be removed, and **Add** is disabled with a tooltip that says why at 8 playlists or when every stored playlist is in the list. A playlist of the list that is not stored (deleted after it was chosen) is marked "Not stored", and a warning says the board skips it and that a change of the list leaves out what the board does not store, since the board accepts only stored playlists. While the reply to a change is awaited, the list and the radio buttons are disabled; the board's answer then replaces the list, or the old order comes back with the error.

**My choice, Schedule:** one menu, **Schedule**, of the schedules stored on the board (ID and name), showing the `schedule` setting, with now, the next change and **Show the schedule** as in Automatic (now from `status.play` while My choice, Schedule plays, else what the schedule plays today). A board that stores no schedule has the Schedule side disabled, with a line and a link, "This board stores no schedule. Add one in the Schedules tab of Files", that opens the Files section on its Schedules tab and moves the focus to the tab. When the setting names a schedule the board does not store (it was deleted, or never uploaded), the menu shows it as "(not stored)" and a warning says that the board plays its own rule meanwhile ("The schedule summer is not stored, so the board plays the schedule default while it is chosen.").

The reordering follows the [playlist editor](#playlist-editor): the handle is for a pointer only and is hidden from screen readers, the **Up** and **Down** buttons move an item one place from the keyboard and focus moves to the item's other move button at the top or the bottom, and every move, addition and removal is announced in a polite live region ("holiday moved to position 1 of 2.").

**Time** has three fields:

- **Time zone:** a menu of the zones of the app's table (the browser's first, marked "this browser"), showing the zone whose POSIX TZ string is the board's `timezone`, the browser's when it has the same rules. Choosing one sends `settings_set {timezone}` with the zone's POSIX string, converted with the same table as before. When the browser's zone has other rules than the board's, a line says so and **Use** with the browser's zone sends it; a zone the table does not have is said, and the user chooses one with the same rules. A board `timezone` the table does not know is shown as it is. The schedule and the install window both read this setting: on such a board the Updates card sends no time zone with a change of the window, and says which zone the board uses and that it is set under Time.
- **Time sync every (hours):** 1 to 168, sent as `time_sync_hours` when the user leaves the field or presses Enter; a value outside the range is refused with a message and nothing is sent.
- **Time server:** the `ntp_server` setting, checked in the field (a host name or an IPv4 address, 1 to 64 characters, letters, digits, dots and hyphens), sent with **Save server**, and **Reset to pool.ntp.org** puts back the default. A note under it says what the board does with it, see [Privacy](#privacy). When the settings cannot be read, the Settings card says "Could not read the board's settings." with a **Retry** that reads the settings again and nothing else.

### Storage

A **Storage** card between the Files card and Settings, when the board reports `info.storage` (the connection chip's details keep showing it too):

- **Space:** "239.0 KB free of 960.0 KB" (sizes as in the file lists, base 1,024) and a bar of the used part.
- **Files:** once every list is read, the schedules included on a board whose `info` reports `formats.schedule`, how many animations and playlists are stored (and schedules, on such a board), and an estimate: "Estimate: about 150 more animations of average size (6.0 KB each) would fit." The average is taken over the stored animations, each rounded up to the file system's 4,096-byte blocks, and the number is the free space divided by it, rounded down. It says "estimate" because the files of the next upload differ. With no animation stored it reads "Store an animation to see how many more would fit." and gives no number.
- **Warnings:** "The board is full. Delete files you do not need before uploading more." when less than one block is free, and "Space is low: less than one animation of average size is left. ..." when the free space is below the average animation (below one block when none is stored).
- **Freshness:** the card reads `info` again after every upload, deletion and Delete everything, with the lists, and when a check or an installation of the board's own updates that the app saw running ends, since it may have stored files.

The Library view has no storage card: its install actions go through the upload queue, which already compares the files with the free space before it sends anything and refuses what does not fit with the numbers (see [Upload queue](#upload-queue)), and the Board view, one click away, shows the space for the user who wants to make room.

### WiFi

A **WiFi** card under Settings, when the board's firmware knows `status`:

- **State:** the connection state of [`status`](../protocol/protocol-v1.md#status) in words ("Connected", "Network not found", "Wrong password", "Joined the network but got no address: the network may block new devices", ...), the name of the stored network ("none" when no network is stored), the address, the hostname and the signal with its quality word (excellent, good, fair, weak). The network name is the board's `wifi.ssid`, shown over USB and over WiFi as text, whatever bytes it holds: it is never read as HTML, it wraps when it is long, and a text direction override inside it stays inside its own line.
- **Set up WiFi** opens a dialog that lists up to 16 distinct networks the board reports, ordered by signal strength, and asks for the password, then sends them with Improv on the same serial port and waits for the result. The board sends at most 16, and the app also bounds its list if another Improv peer reports more. **Other network** lets the user type any name. The app closes its protocol connection only if Improv needs the port alone; it reconnects afterwards. **Forget network** sends `wifi_forget` after a confirmation.
- **Transmit power:** a menu with Auto and the fixed values, sent with `settings_set {wifi_power}`, with the legend of [Transmit power](../board/wifi-and-updates-v1.md#transmit-power). When `power_reduced` is true, a note says the board lowered the power by itself.

Over WiFi the card shows the state but not Set up WiFi or Forget network, which need USB: a note says so in their place.

### Updates

An **Updates** card under WiFi:

- **Mode:** Off, Notify, Automatic, with one line each on what they do. A board that was never set has the mode Automatic, the default of the firmware.
- **Firmware updates** and **Animation updates** switches. Under Animation updates, a note: "The release wins: animations, playlists and schedules with the same name are replaced, and deleted ones come back. Turn this off to keep local changes."
- **Check every** (hours, 1 to 168), sent when the user leaves the field or presses Enter; a value outside the range is refused with a message and nothing is sent.
- The **install window** (from and to, as times of day; "whole day" when they are equal, "over midnight" when the end is before the start; a line under the fields reads "Install window: whole day. Choose two different times to narrow it." for equal times), with the time zone taken from the browser and sent as a POSIX TZ string from a table the app carries. The app sends the browser's time zone together with a change of the window when the board has another, and says which zone the board uses. A time zone the table does not have is not sent: the card says that the app does not know its rules and which zone the board uses. On a board that reports `formats.schedule`, the time zone is the **Time zone** field of the [Settings](#settings) card instead: the window sends none, and the card says the board's zone and that it is set under Time.
- **Animation source:** the manifest URL (**Reset to default** puts back the `manifest.json` next to the page the app is served from, so a fork's app resets to its own release; a page on `localhost`, on a file, on plain `http` or on the development server uses the project's `https://monska85.github.io/PixelArt/manifest.json`), checked in the field (http or https, a host, no user name or password, plain ASCII, at most 512 characters) and sent with **Save source**, with **Reset to default**.
- **Status:** the running firmware, the last check ("12 minutes ago", or "not since the board started") and its result (for the [update error](../protocol/protocol-v1.md#update-errors) `http_error` with the detail `no_release`, the board's manifest request was answered 404, the card says "No release is published at this address yet. Check the animation source, or try again after the first release." instead of the words of an HTTP error; the other errors keep their words and code), what is available (a firmware version, a number of files), the last installation (updated or rolled back, with the versions), and a progress bar while a check or an installation runs. The app reads `status` every 2 seconds while something runs, and every 10 seconds otherwise, so the WiFi state stays current. Each view reads it once for all its cards, and not while the connection is lost, an upload runs or the WiFi setup dialog is open.
- **Check now** sends `update_check`; **Install firmware** and **Install animations** send `update_install` when something is available. The buttons are disabled, with a tooltip that says why, when updates are off, a check or an installation runs, the board is not connected to WiFi, or (for the installation) the last check found nothing. **Install firmware** sends `update_install` with the target `firmware` after a confirmation: "Install firmware 1.3.0?", saying that the board downloads it, checks it and restarts, that the animation stops and the matrix shows a progress bar meanwhile, that the animations, playlists, schedules and settings stay, and that the board goes back to the running version by itself if the new one does not start properly. The button is disabled, with a tooltip that says why, when updates or the firmware switch are off, a check or an installation runs, the board is not connected to WiFi, or the last check found no firmware. While the firmware installs, the card shows the progress bar and a note that the board restarts and the app may lose the connection for a moment. A version the board skipped after a rollback (the available firmware is the `to` of a `rolled_back` last installation) is shown as rolled back and not installed by the board itself; installing it asks another question, "Install firmware 1.3.0 again?" with the button **Install anyway**, and sends `force: true`. When the installation ends with the restart, the status shows the last installation as updated, or as rolled back with both versions once the board went back; when it fails before the restart, the status shows the error, the firmware stays on offer, and the button works again.

### Network access

A **Network access** card under Updates, shown when the board has the `network_login` setting:

- **Network login** switch, sent with `settings_set {network_login}`. Under it, while the switch is off, the warning "When this is off, anyone on your network can change this board's animations and settings."; while it is on, a note that WiFi clients log in with the token and that the traffic is not encrypted. A client that turns it on over WiFi is asked to log in at once, with the dialog above when the browser has no token for the board.
- **Token** (USB only): the board sends it only over USB, so over WiFi the card says that the token is shown over USB only. Over USB it is shown hidden (16 bullets) with **Show** (then **Hide**) and **Copy**, and **Regenerate** after a confirmation, "Make a new token?", that says the old token stops working and WiFi clients have to log in again, since the board closes the WiFi connection. The new token is shown hidden again.
- **Certificate** (USB only, only if the board serves `wss://`): **Regenerate** after a confirmation. The firmware of this version has none, and the card has no such row.

The **Delete everything** dialog (Board view and Firmware view) says that the reset also restores every setting, forgets the WiFi network and makes a new token, and over WiFi its **Also reset the settings** box is disabled, with a tooltip saying it needs USB, see [Delete everything](#delete-everything).

### Missing animations

A stored playlist can name animations the board does not store (they were deleted, or never uploaded). The app reads each stored playlist from the board and compares the animations it names, enabled or not, with the stored animation list. Nothing is called missing while a list is not known (still being read, or unreadable), or while a playlist could not be read.

- **Files card:** the warning of the summary, see [Files](#files).
- **Playlists tab:** a playlist with missing animations shows a warning badge with an icon and the word, "2 missing", next to its name. A tooltip (also on keyboard focus) lists at most 10 missing animations, then "and N more", so it stays shorter than the screen; the accessible name lists them all. A row **Install missing** icon button sends the missing animations that `./manifest.json` publishes through the [upload queue](#upload-queue); the ones that are not published are listed in the tooltip as "not available in the Library". The button is not shown when none of them is published.
- **Settings card:** the active playlist (see [Settings](#settings)) gets the same warning as a note with the list (at most 10 names, then "and N more"; assistive technology reads them all), "Not available in the Library: ..." for the unpublished ones, and an **Install missing** button.
- **Playlist editor:** each item whose animation is not stored is marked "Not stored". When the release publishes it, the item has an **Install** icon button for that animation; otherwise it says "Not available in the Library".

### Playlist editor

Edits any stored playlist (**Edit** in the Playlists tab), or a new one (**New playlist**) with an ID the user chooses (the ID rule applies). The editor opens in a wide panel of the [list pattern](#list-pattern), so it is in view however many files are stored and an item fits on one line on a wide screen; its footer has **Cancel** and **Upload to board**. It shows the playlist's name and its items in order. For each item: the animation (a menu of the stored animations, plus the current value when it is not stored), `repeat` (1 to 1,000) and `enabled`. Items can be added, removed and moved up and down, with the **Up** and **Down** icon buttons or, with a pointer, with the drag handle at the start of each item:

- **With a pointer** (mouse, pen or touch), dragging the handle moves the item over the others: it takes its new place as soon as the pointer passes the middle of another item, and it is marked while it moves. Near the edge of the scrolling area the list scrolls, and keeps scrolling while the pointer rests there; it stops when the pointer leaves the edge, the list cannot scroll further, or the drag ends or is canceled. The edge zone is 48 px, or 15% of the area's height when that is smaller, measured from where the list shows: below a bar that sticks to the top of the area (the panel's title) and above one that sticks to its bottom (its buttons). Both directions use the same zone and the same speed; the browser's scroll anchoring is off while an item is dragged, since it would shift the list each time the item passes the one the browser anchors to and make scrolling up several times faster than down. The speed grows with how deep the pointer is in the zone, from 3 px per 60 Hz frame at its outer limit to 14 px at the very edge, measured by time so it is the same at any frame rate; a drag that starts inside the zone waits 300 ms before the list scrolls. Releasing drops it; a canceled touch puts it back.
- **With the keyboard**, the **Up** and **Down** buttons move an item one place; focus stays on the button of the moved item, so pressing it again keeps moving the same item. When the move reaches the top or the bottom, that button is disabled and focus goes to the item's other move button. After **Remove**, focus goes to the **Remove** button of the item that takes its place, or of the item before it when the last one went, or to **Add animation** when the list is empty (to the name field when no animation can be added). The handle is for a pointer only: it is not focusable and is hidden from screen readers (its tooltip "Drag to reorder" is the browser's own), so nothing in the tab order does nothing.
- **Every move is announced** to screen readers in a polite live region: a move with **Up** or **Down** ("ball moved to position 2 of 12."), the end of a drag ("ball dropped at position 2 of 12.", or "ball dropped at its place, position 3 of 12." when it did not move), a canceled drag ("Move cancelled. ball is back at position 3 of 12.") and a removal ("ball removed. 11 items left.", or "No items left." for the last one).
- **A missing animation's mark** ("Not stored", with **Install** when the Library has it) sits under the item's animation field, aligned with it.

No drag-and-drop library is used: the handles work with the browser's pointer events, which adds nothing to the download. The repeat field can be emptied while the user types; it takes the number once it is a whole number from 1 to 1,000, and shows the stored value again when the field loses focus with anything else in it. **New playlist** is unavailable while the editor is open. **Edit** on another playlist while the editor has unsaved changes asks first ("Discard the unsaved changes to playlist ID and open playlist ID?", with **Discard and open** and **Keep editing**; a playlist is named by its ID, and one that has no ID yet is called "the new playlist"). A repeat field with anything other than a whole number from 1 to 1,000 shows "Whole number from 1 to 1,000." next to it. Every opening moves focus to the editor's heading.

**Upload to board** builds the playlist document, validates it with the app's engine, and sends it through the [upload queue](#upload-queue) as a single file, so it gets the same space check. A new playlist whose ID the board already stores asks the queue's question about a differing file; an opened playlist replaces the stored one without a question, and a playlist the board already stores unchanged is not sent again. The panel shows the result, with a toast, and not the queue's own alerts. When nothing was sent because the user answered **Cancel**, or **Keep the board's** to the question about a stored ID, a toast says so ("Nothing was sent", "Kept the board's playlist ID; nothing was sent") and the panel stays open. Items that name an animation that is not stored are allowed and marked, and the queue does not ask about them: the board stores the playlist with an `unknown_animation` warning, which the panel shows (for an unchanged playlist the app shows the same warning itself). The saved document keeps the fields of the original and writes `repeat` and `enabled` only when they differ from their defaults.

## Privacy

The privacy promise is a contract with the user: nothing personal leaves the browser and the board. It is stated in three places: a short version in the [footer](#app-shell), the notes where sensitive data is entered, and the **Privacy** view. A change that makes any private or sensitive information leave the browser or the board, or that adds an outside service, request, analytics, telemetry or third-party script, changes all of them, this document and the README in the same change, and is approved by the user first (AGENTS.md).

- **Footer:** the line described in [App shell](#app-shell).
- **Notes where data is entered:** next to the password of the WiFi setup dialog, "The password goes straight to the board over USB. It is never sent anywhere else.", above the token of the Network access card, which shows the token the board gives over USB, "Read from the board over USB. The app does not store it or send it anywhere: over WiFi the board checks a code derived from it.", in the login dialog, where a token is typed and then kept in this browser, "Kept in this browser to log in again. It is never sent: the board checks a code derived from it.", and under the Time server field of the Settings card, "The board asks this server for the time when the board plays a schedule or the install window is narrower than the whole day. The request carries none of your data; the server sees the board's IP address."
- **Privacy view:** at the address `#privacy`, reached from the footer only (it is not in the navigation). Its sections:
  - **What stays in your browser:** every key the app writes to browser storage, by purpose: `pixelart.theme` (the theme choice), `pixelart.simulator` (the simulator address last typed), `pixelart.wifi` (the address of the board on your network, its name ending in `.local` or the address typed, from the last WiFi connection or read from the board over USB), `pixelart.token.<host>` (the token of the board at that address, stored as written, to log in over WiFi again; never sent, only a code derived from it), `pixelart.editorNote` (the dismissed Editor note), `pixelart.boardFiles` (whether the Board view's Files section is open or closed), all in `localStorage`, and the editor draft in IndexedDB (database `pixelart-editor`, store `drafts`, key `current`). The app sets no cookies. A unit test keeps this list equal to the keys in the source.
  - **What goes only to your board:** uploaded files, settings, the WiFi network name and password (over USB only, with Improv). To log in over WiFi the app sends a code derived from the token with the board's one-time number, never the token.
  - **What your board contacts:** to check for updates the board itself contacts the release site (the firmware manifest) and the animation source. For the time it asks the time server of its Time server setting (pool.ntp.org unless the user changes it), and only while it needs the time: when the board plays a schedule, or when the install window is narrower than the whole day. Those requests carry none of the user's data, and those hosts see the board's IP address. Setting the update mode to Off stops the update checks; the time requests stop when no schedule and no narrow install window needs the time. The web app itself makes no request for the time: the time zone comes from the browser, and the schedule the app shows comes from the board or from the site.
  - **Limits:** the WebSocket to the board is plain `ws:`, so on the local network someone who can watch the traffic can see what is sent and the network name in `status`, and with the network login off there is no login at all; the board keeps the WiFi network name and password in plain text, readable by anyone who holds it; the token is stored in the browser as written (clear text), readable by anyone with access to that browser profile.
  - **What the site sees:** the site only serves files (the app, the manifest of the release, the animations, the playlists, the schedules and the firmware), the app loads them from its own address only, and it makes no request to any other site and uses no font, analytics, error reporting or other third-party service. The host (GitHub Pages) sees the standard data of every request, such as the IP address, the user agent and the files asked for, like any website.
  - **Check it yourself:** the project is free software under GPL-3.0-or-later, with a link to the repository (its address is written as text from the same address, `github.com/<owner>/<name>`), the content security policy of `web/index.html`, the web app source in `web/src` and the firmware source in `src/` and `lib/`.
  - **Licenses:** the version of the app (the `version` of `web/package.json`) with a link to the tree of its tag `web-vX.Y.Z` on the repository, or for a version that is not a release (`0.0.0`, a pre-release) a note saying so with a link to the repository; relative links to `LICENSE.txt` and `LICENSE-EXCEPTION.txt`, which the build publishes next to the notices; and links to the third-party notices of the web app (`./THIRD_PARTY_NOTICES.txt`) and of the firmware the site publishes (`./firmware/THIRD_PARTY_NOTICES.txt`).

The content security policy in `web/index.html` is what makes the claim about requests checkable: `default-src 'self'` (everything the page loads comes from its own site), `script-src`, `font-src` and `img-src` the same, and `connect-src 'self' ws:`: the page can reach no other site over HTTP or HTTPS, and it can open a WebSocket to any address (how it reaches a board on the network, whose address is not known in advance), but the app opens one only to the board the user chooses. A unit test compares the whole policy, every directive and token, with the one above, and fails when a module other than the two that read the release files and the one that opens the WebSocket uses a network or dynamic-code API, when browser storage is reached other than through the helpers with a listed key, or when the source, the page or the styles name a site that is not listed. An end-to-end test watches every request of the browser context and its WebSockets while the views and the on-demand flows run, and expects no other host and no service worker. The development server does not send the policy.

## Library view

Lists the animations and playlists published in `./manifest.json` (see [Latest release](#latest-release)), with their name and version, and a preview of each animation. The page description names the content release they come from, the manifest's `content_version` ("Animations published with content release 1.4.0"); a manifest without it, from a firmware release published before the content package, gives its `version` instead ("Animations published with release 1.2.0"). Without a manifest (nothing published yet, or running from `make web-dev`), the view says that nothing is published.

For a kind declared in `content_pages`, the Library uses the complete paged catalog, including a declared empty one, instead of its legacy list. It fetches each bounded page from the same site, checks its exact size and SHA-256, and rejects the entire manifest load if a declared page is missing, malformed or inconsistent. It does not show a partial catalog or fall back to legacy entries. A kind without pages uses its legacy list, so older releases remain available. The same loaded catalog supplies the content installation after a first firmware install, missing-animation actions and the site's schedule preview.

When a board is connected, each entry shows whether the board has it:

- **Not on the board:** no stored file with that ID.
- **Same:** the stored file has the published SHA-256.
- **Different:** the stored file has another SHA-256 (another version or a local change).

The lists follow the [list pattern](#list-pattern), like the Board view, with the state on the board as a column; the row actions are the icon buttons **Install** (on every row, disabled with a tooltip on the ones the board already has the same), **Preview** and **Open in editor** (animations), with no menu, because no row has two actions to fold away. **Install** downloads the published file, checks its size and SHA-256 against the manifest, and sends it through the [upload queue](#upload-queue). On a playlist, the install brings the animations it names (the button's tooltip says so). The **Install all** menu in the page header offers all animations, all playlists, or everything, with their counts. On a board whose `info` reports `formats.schedule`, everything also installs the published schedules, after the playlists, and counts them; a board whose firmware is older than schedules gets the animations and playlists only. The Library has no list of schedules, and everything does not install the play file: the site's choice for Automatic comes with the board's updates and with the USB install of a first install. Files the board already has identical are skipped, and differing ones are asked about once.

## Firmware view

### Latest release

The app reads `./manifest.json`, relative to its own address (its optional `play` list is the site's choice for Automatic, which the USB install of the content sends to the board as a file), with `cache: "no-cache"`, so the browser checks with the server instead of using a copy up to 10 minutes old. A manifest that does not load, is not valid JSON, or has a `format` other than `pixelart-manifest/1` counts as no release; the view then says that no firmware release is published yet. So does a manifest without a `firmware` list or with an empty one, which a site with a content release and no firmware release serves: its `version` is a content version, never compared with a board's firmware. The Library still lists its animations and playlists.

### Version check

When a board is connected, the view compares `info.firmware` with the manifest's `version` by Semantic Versioning precedence:

The status card says "This board runs Y. The latest release is X." and a badge gives the result:

- **Older:** the badge "Update available".
- **Same:** "Up to date".
- **Newer** (a board built from a newer commit): "Newer than the release".
- **Development builds** report versions such as `1.2.0-dev.3+gabc1234` or `0.0.0-unknown`. A pre-release sorts below its release, so a development build of an older or the same version counts as older; the view adds the badge "Development build".

A version that is not valid Semantic Versioning is shown as it is, with no comparison.

### Updates over WiFi

When a board is connected and knows `status`, the view shows a card **Updates over WiFi** after the status card: the board's own update state, read as the Updates card of the Board view reads it. It lists whether the board is connected to WiFi, what it is doing now (idle, checking, installing with its progress), when it last checked, the firmware its last check found (a version that was rolled back is marked as such), and its last installation (updated, or rolled back with both versions). The card says that the board can install a new firmware by itself and goes back to the previous one if the new one does not start, that the buttons of the view install over USB, and links to the Updates card (the link says "Updates card", followed by "of the Board view"), where the installation over WiFi starts. A board whose firmware does not know `status` gets no such card.

When the board is not connected, the view still offers the install button, since an empty board cannot answer the protocol.

### Install and update

The buttons are ESP Web Tools install buttons, loaded only when the Firmware view opens:

- **Update firmware** uses `./firmware/update.json`: it writes the bootloader, the partition table, `boot_app0` and the firmware, and keeps the animations, playlists, schedules and settings.
- **Install from scratch** uses `./firmware/install.json`: it writes the same parts, and ESP Web Tools offers to erase the board first. Erasing deletes the settings and every stored file. The view says so before the button. The firmware release holds no animations: after an erase the board starts with an empty file system and shows its "no animations" image, and without the erase it keeps the files it stores.

**Animations after a first install.** The Install from scratch card has a checkbox **Then install the animations and playlists** ("Then install the animations, playlists and schedules" when the manifest lists schedules), checked each time the view opens, with the note that the board must stay connected until they are installed. It is disabled, unchecked, when the manifest publishes no animation, no playlist and no schedule. When the box is checked and the ESP Web Tools dialog opened by that button closes after its installation finished, the app installs the content of the latest release over the same USB port:

1. The activity panel says "Installing the animations, playlists and schedules of release 1.4.0" (the manifest's `content_version`, else its `version`). The app opens the port ESP Web Tools used, which the browser already granted, so no port picker opens, and connects as **Connect board** does. The board has just restarted and may still be formatting its file system, so the app tries again every second while the port cannot be opened or the board does not answer (no answer, or a connection that drops). No new attempt starts after 20 seconds, and an attempt under way is not cut short, so the last one can end a few seconds later. Any other refusal, such as a board whose protocol this app does not know, stops it at once, with the reason.
2. It sends every published animation, every published playlist and, only to a board whose `info` reports `formats.schedule`, every published schedule through the [upload queue](#upload-queue), as **Install all**, everything, does in the Library view: downloaded and checked against the manifest, then compared with the board. A manifest without `schedules` (an older release) has none to send. After an erase every file is missing; without the erase, files that differ are asked about once, as for any upload.
3. As the last file of the same queue, after the schedules, and only to a board whose `info` reports `formats.play`, it uploads the published play file (the `play` list of the manifest, `play/default.json`, which names the schedule or the playlists the release says Automatic plays), like any other file, as an update check over WiFi would install it. A board that gets its content over USB has no check to read the manifest, so this is how it learns what Automatic plays. The play file is part of the same reservation of the upload queue, so no other upload can start between the files and the play file. A refused install (the queue is busy, the board cannot be read, the space does not fit), a cancelled one and one stopped by a failed upload send no play file: Automatic changes only once the play file is stored. A manifest without `play`, or a board without `formats.play`, has none to send.
4. The queue's summary says what was installed, and the Board view shows the files.

When the board cannot be reached in that time, the app shows an alert, "The animations, playlists and schedules were not installed", which says the board shows its "no animations" image until it gets them, with **Connect board** and a link to the Library view, where **Install all**, everything, installs them. A failure of the queue is reported as the queue reports it, and running it again from the Library resumes. When the dialog closes before an installation finished (canceled, failed, or closed at its first page), nothing more happens. The box does nothing for **Update firmware**, which never changes the stored files. The app learns that the installation finished from the state of the ESP Web Tools dialog it observes when the dialog closes, since ESP Web Tools sends no event for it; the version of ESP Web Tools is pinned, and a change of that state is caught by the unit test that covers it.

**Old flash layout.** A board flashed before the firmware with WiFi has the old flash layout (the Arduino default for 4 MB flash). Update firmware writes the current partition table but cannot move the stored files to it, so such a board needs one Install from scratch with the erase. The app recognizes such a board by the size of its file system in `info`, 1,441,792 bytes (`0x160000`), against 983,040 (`0xF0000`) on the current layout. When the connected board reports that size, the status card shows a warning, "This board needs Install from scratch once", which says that Update firmware cannot move the stored files to the current layout, and that Install from scratch with the erase deletes the animations, playlists and settings, that the app then installs the published ones, and that later updates keep them. The Install from scratch card says in its description that it is also needed once for such a board. A board of another size gets no warning.

ESP Web Tools detects the chip and picks the matching build (ESP32-C3, ESP32, ESP32-S3) from the manifest.

The serial port can only be open once, so the app closes its own connection before ESP Web Tools opens the port, and says so. After the installation the board restarts; the app offers "Connect board" again and then shows the new version.

## Editor view

The editor opens an animation from a file (`.yaml`, `.yml`, `.json`), from the board (Edit in the Board view), from the Library, or as a new animation from a template. It edits the whole `pixelart/1` format.

### Opening a document

Every opening shows what the user asked for, never an older document or a stored draft. A draft that the browser's storage returns late (after 3 seconds) is restored only if nothing was opened or edited meanwhile.

- **Without unsaved changes** the new document opens at once. A restored draft that had no unsaved changes counts as none.
- **With unsaved changes** a dialog appears at once, in the view where the user is (an **Edit** in the Board view or an **Open in editor** in the Library view asks there, not after a jump to the Editor): "Discard the unsaved changes to NAME and open NAME?", with **Discard and open** and **Keep editing**. Escape also keeps the document. Names are the `name` of each animation, or where it came from when it has none. The app then shows the Editor with the document the user ended up with, also after **Keep editing**. An opening replaced by a newer one does not show the Editor; the newer one decides.
- **The Editor menu item** only shows the document being edited and opens nothing.
- **Back:** when an animation was opened from the Board view (**Edit**) or the Library view (**Open in editor**), the Editor shows **Back to Board** or **Back to Library** above the toolbar. It stays while that document is edited, also after the user has been to another view and returned with the menu. The way back is stored with the draft, so it also stays after a reload. Opening a file or a new animation shows no such button. After the user presses **Back**, keyboard focus moves to the heading of the view shown.
- **After Upload to board** succeeds, the editor stays open and shows the success note next to the upload button, with the way back still there. Opening another document clears that note and any other save or upload result. Returning to the Board view reads the files again, so the uploaded file is in the list.

### Layout

- **Palette:** the named colors, each with its name and a color picker with a hex field. Colors can be added, renamed and deleted. Renaming a color updates every place that uses its name; deleting one that is used asks first, then replaces it with its hex value in every place. The current drawing color is a palette entry or a hex value.
- **Sprites:** the list of sprites, with add, rename (references follow), duplicate and delete (a sprite still referenced asks first). Each sprite is either a points sprite or a composite.
- **Grid:** a 16x16 grid for the selected points sprite, drawn at its home position `at`. Tools: draw (current color), erase, pick a color from the grid. Moving the sprite changes `at`. Points outside the 16x16 canvas are kept and listed under the grid; they are edited in the YAML tab. The sprite's `pivot` is set with a field and shown on the grid.
- **Composite:** for a composite sprite, its parts in order, each a sprite and an optional `at` for this composite only; parts can be added, removed and moved.
- **Timeline:** the items in order, frames and loops nested as in the file. Items can be added, duplicated, deleted, moved, and put into or taken out of a loop. A loop has its count. A frame has `ms` (empty means the animation's `frame_ms`), `repeat`, `recolor` (pairs of colors) and its `show` list. Each entry of `show` is a sprite and the optional fields of a sprite reference: `at`, `move`, `wrap`, `rotate`, `spin`, `flip` and `pivot`, as form fields.
- **Animation:** `name`, `version`, `author`, `description`, `frame_ms`, `brightness` (1 to 100 percent of the board setting) and `background`.
- **YAML tab:** the whole document as YAML text, see [YAML tab](#yaml-tab).
- **Preview:** the animation played by the app's engine, with play, pause, step, the frame number and the timeline item that produced the frame. Selecting a timeline item moves the preview to its first frame.
- **Diagnostics:** the engine's errors and warnings for the current document, updated as the user edits, in the table described under [Errors](#errors).

Every change can be undone and redone (at least 100 steps): Ctrl or Cmd+Z undoes, and Shift+Ctrl or Cmd+Z, or Ctrl+Y, redoes.

### Writing the document

The editor keeps the document as data and changes only what the user changed. Fields keep their order. A sprite whose points are edited on the grid is written with its points grouped by color, in the order in which each color first appears on the grid row by row; other sprites keep the form they had. Optional fields equal to their default are left out when the editor creates them, and kept when the file had them.

### YAML tab

The YAML tab shows the document as YAML and accepts edits. While the text is not valid YAML, the visual editor keeps the last valid document and the tab shows the parse error with its line. When the text parses, it replaces the document and the visual editor follows. Comments are kept in the YAML tab while the user edits there; a change made in the visual editor rewrites the text and drops the comments, and the tab says so.

### Where the work is saved

The editor's document has two real copies only: the file on a board (**Upload to board**) and a YAML file the user downloads (**Download YAML**). The browser draft (see [Saving](#saving)) protects against a reload, but it is not a backup: it is lost when the browser's data is cleared, and it is not on another browser or computer. The editor makes this visible at all times.

- **Save state.** The editor header always shows where the current version lives:
  - **Draft in this browser only**, in the warning color, for a new animation, an animation from the Library, or any document never uploaded or downloaded since it was opened.
  - **Saved to board as `<id>` at `<time>`** after an upload, or when the animation was opened from the board with **Edit** (the time is then the opening).
  - **Downloaded as `<id>.yaml` at `<time>`** after **Download YAML**, or **Same as `<file name>`** for a document opened from a file.
  - **Changed since** in front of the last one (for example "Changed since: saved to board as `ball` at 10:42", or "Changed since: opened from `ball.yaml`" for a file), in the warning color, when the document differs from what was last uploaded or downloaded. The comparison is on the document's content, so undoing back to the saved version shows it as saved again.
  - Times are the browser's local time as `HH:MM` (24 hours).
  - When both copies exist and are current, the header shows the most recent, and its tooltip lists both; the tooltip marks an older version of a copy that no longer matches.
  - A document opened with **Open file** starts as **Same as** that file; a new document and one opened from the Library start as a draft.
  - The save state is kept with the draft, so it is still right after a reload.
  - When a board is connected, "Saved to board" is checked against that board's files: if the board has no file with that ID, or one with another SHA-256 (another board, or the file was changed or deleted), the header says **Not on the connected board** instead, unless a current download exists.
  - The board's file lists are read again when a board connects or restarts, when the Editor view opens, and after every upload, delete and **Delete everything**, so a file removed from any view is noticed at once.
  - While nothing is known about the board's files (the first read after connecting is not done, or the last read failed), the header says **Board copy not checked**, in the warning color, unless a current download exists.
  - During a re-read after a change, the header is judged by the last known list. A copy the editor saved after that read began counts as on the board until the new list arrives, so an upload from the editor never makes the header flicker to a warning.
- **The two saves are the primary actions.** **Upload to board** (primary button) and **Download YAML** stay in the editor header, next to the save state, in every tab.
- **First use.** The first time the editor opens in a browser, a short note explains: "Your work is kept in this browser as a draft. It is not a backup: clearing the browser's data, using another browser, or deleting the animation from the board can lose it. Upload to board or download the YAML file to keep it." **Got it** hides it for good in that browser (if the browser refuses to remember, the note shows again next time).
- **Leaving the page.** While the document has changes saved nowhere (the save state is "Draft in this browser only" with changes, or "Changed since"), closing the tab, reloading or leaving the page asks the browser's standard question first. The question is also asked for "Not on the connected board" or "Board copy not checked" with no current download, since the board file may be the only copy. Without a connected board the board copy counts. An unchanged new animation, and an opened document with no change, can be left without a question; so can a changed one after an undo back to a saved version. A YAML tab with an error always counts as unsaved.
- **Deleting the only copy.** When the editor holds an animation whose only saved copy is the board file about to be deleted (the save state is "Saved to board" for that ID, with no current download), the confirmation of **Delete** in the Board view, and of **Delete everything**, adds: "The editor holds this animation and it has no other saved copy." with a **Download YAML first** button next to the confirm button. The button downloads the editor's YAML as `<id>.yaml` and the warning goes away, since the document then has a second copy. While the YAML tab has an error, the download is refused, as for **Download YAML**.

### Saving

- **Download YAML:** downloads `<id>.yaml`, in the format the repository uses: the same document the editor shows, hex colors quoted. While the YAML tab has an error, nothing is saved and the editor says so, because the file would not match the text on screen. **Upload to board** is refused the same way, before it asks for an ID, because the board would receive the last valid document and not the text on screen; the document stays unsaved.
- **Upload to board:** converts and uploads like the Board view's [Upload](#upload) through the [upload queue](#upload-queue), with the ID chosen at the first save. The result is shown next to the buttons instead of as a toast: uploaded, "The board already has this exact animation" (a file that is identical counts as saved to the board), skipped (**Keep the board's**) or canceled.
- **Drafts:** the document being edited is kept in the browser's storage shortly after every change (a short delay joins quick changes into one write), so a reload or a closed tab does not lose it. Drafts stay in the browser that made them; files on the board and saved YAML files are the real copies, see [Where the work is saved](#where-the-work-is-saved).
- **A restored draft:** when the app starts and finds a draft, the editor brings it back, whichever view the page shows. The draft records whether the document had unsaved changes. A draft with unsaved changes shows a note, in the Editor view, with the time it was saved; a draft without them comes back silently and is replaced by the next opening without a question. **Dismiss** hides the note and keeps the draft. **Discard the draft** deletes it and starts from a new animation. The **Discard the draft** item of the editor's More menu does the same after a confirmation.
- **When the page crashes:** if drawing a view fails, that view is replaced by a notice with the error message, and the top bar still works. **Reload the page** is offered in every view, and the draft comes back when the page loads again. Only in the editor, a second action, **Discard the draft and start again**, deletes the stored draft and reloads, so a draft that crashes the editor cannot make every visit crash. It first asks for confirmation and says that the draft will be deleted. A crash in another view never offers it, because the draft is not the cause.

## Engine

The app has its own implementation of the formats, in TypeScript, with no access to the page: it runs in the browser and in Node for the tests. It parses, validates and plays `pixelart/1` and `pixelart-playlist/1`, and parses, validates and resolves `pixelart-schedule/1`, and validates the play file `pixelart-play/1` (the site's choice for Automatic, 1 KiB at most), exactly as the engine in `lib/PixelEngine/` does: the same limits, the same error and warning codes, the same `where` places, at most 32 diagnostics per file with the same rule for which ones are kept, and the same frames. The text of messages may differ.

- `loadAnimation(bytes)` returns the animation, or the diagnostics that reject it. The input is the file's bytes, so the app checks exactly what it uploads.
- A player gives the frames in order: for each, its duration and the color of each of the 256 pixels.
- `loadPlaylist(bytes)` returns the enabled items, or the diagnostics.
- `loadSchedule(bytes)` returns the schedule (its name, its fallback and its entries in the order of the file), or the diagnostics.
- `scheduleWinner(schedule, date)` gives the entry that wins on a local date by the [winner rules](../format/schedule-v1.md#which-entry-wins), the first tied entry on a tie, looking at each entry once; `choosePlaylists(mode, playlists, schedule, date, playable)` gives the list the board plays, the reason, the winning entry and the playlist that plays, as [How the board chooses what to play](../format/playlist-v1.md#how-the-board-chooses-what-to-play) says. Both resolve one date and never loop over years.
- `nextScheduleChange(schedule, today)` gives the first day after today, at most 366 days ahead, on which the schedule names other playlists, for the Automatic card.
- `effectiveBrightness(board, percent)` implements the [brightness rule](../format/pixelart-v1.md#brightness).

Both engines read strict JSON as the [format specification](../format/pixelart-v1.md#files) requires. The browser's `JSON.parse` turns `1.0` into the integer 1, but `1.0` is not an integer in the format, so the engine has its own JSON reader that keeps integers and other numbers apart.

The engine passes every case of the [conformance suite](../../conformance/README.md), checked in CI. The suite is the contract between the two engines: a difference between them is fixed with a new case that both must pass.

## YAML

The app reads YAML the way `tools/pixelart.py` does, so a file gives the same JSON in the app and on the command line:

- YAML 1.1 rules, as PyYAML applies them: `yes`, `no`, `on` and `off` are booleans, and numbers keep their YAML 1.1 forms.
- A key repeated in the same mapping, or a key that is not a string, is an error.
- Only plain data: no custom tags, no aliases that build unbounded structures (the reader refuses a document in which aliases expand to more than 100,000 nodes in total, and YAML text over 256 KiB).
- The JSON is written compact, with no spaces, keys in the order of the YAML text, and characters outside ASCII written as they are (UTF-8), without a final newline.
- A YAML number with a fraction or an exponent stays a non-integer in the JSON (written with a fraction, for example `100.0`), so the engine rejects it where an integer is required, exactly as it would reject the command line's output.

For every animation, playlist and schedule of the repository, the app's conversion gives the same bytes as `make data`. A test checks it.

Converting JSON back to YAML (Download as YAML, the YAML tab) writes block style for mappings, flow style for points and coordinate pairs, and quotes every hex color.

## Publishing

The firmware, the content (the animations, playlists and schedules) and the web app are released separately by release-please, as [Releases](../../README.md#releases) in the README describes: which commits belong to which package, the tags, the changelogs and the release steps. The web app's version is in `web/package.json`, and a web release attaches `pixelart-web-<version>.zip`, the built app, and its `THIRD_PARTY_NOTICES.txt` to its GitHub Release, and ends the release's description with a line on the source code and the licenses: the tag, the repository, how to build it again (`make web-build`) and where the notices are.

A Pages deployment replaces the whole site, so every deployment publishes the latest firmware release, the latest content release and the latest web release together. After any of the three releases, and on a manual redeploy, for each package the workflow takes the highest release that is neither a draft nor a pre-release, has a tag of the exact form (`vX.Y.Z`, `content-vX.Y.Z` or `web-vX.Y.Z`) and already carries its archive. A newer release that does not carry its archive yet is skipped, because it can still be building or its publish can have failed. A failed query of GitHub Releases fails the job and is never read as "no release". The workflow downloads the three archives and merges them into one folder as [Assembling the site](../format/manifest-v1.md#assembling-the-site) describes, and deploys it. When a package has never been released, the deployment publishes the others without it. The web app's files never overwrite a release file: a name present in two archives fails the deployment.

The published site:

| Path                                                               | Content                                                         |
| ------------------------------------------------------------------ | --------------------------------------------------------------- |
| `index.html`, `assets/`                                            | The web app.                                                    |
| `THIRD_PARTY_NOTICES.txt`                                          | The third-party notices of the web app, see below.              |
| `LICENSE.txt`, `LICENSE-EXCEPTION.txt`                             | The repository's `LICENSE` and `LICENSE-EXCEPTION`, see below.  |
| `manifest.json`, `content-pages/`, `firmware/`, `animations/`, ... | The firmware and content releases, as the manifest format says. |

`make release-site` builds the three from the working tree into `site/`, the site Pages would show if all three were released from that commit.

**Repository address.** The source link in the footer, the repository link and its text in "Check it yourself", the release tag link and the notices header use the repository address from the build (`web/scripts/repository.ts`). In GitHub Actions, `GITHUB_REPOSITORY` provides the `owner/name` used in `https://github.com/<owner>/<name>`. The owner has 1 to 39 letters, digits or hyphens and starts with a letter or digit. The name has 1 to 100 letters, digits, dots, hyphens or underscores and is not `.` or `..`. These are the site address rules; an invalid value fails the build. Other builds use the project's address, `https://github.com/Monska85/PixelArt`, written once in that file. A fork therefore links its own source without code changes.

The build copies `LICENSE` and `LICENSE-EXCEPTION` from the repository root into the site as `LICENSE.txt` and `LICENSE-EXCEPTION.txt`. The extensions make a static host serve them as text the browser shows, like the notices. The build fails when either source file is missing.

**Third-party notices.** The build writes `THIRD_PARTY_NOTICES.txt` next to `index.html` (`web/scripts/notices.ts`, with `rollup-plugin-license`). It lists, with the version, license and source of each and then the full text of every license once, numbered:

- the fixed entries: the components of `web/src/ui/components`, based on shadcn/ui (MIT), and the esptool flasher stubs that esptool-js bundles and ESP Web Tools sends to a board (GPL-2.0-or-later, with the releases of `esptool-legacy-flasher-stub` that hold their source);
- every npm package the bundle holds code of;
- the dependency tree of each package that is published already bundled, ESP Web Tools, as installed: the bundler sees such a package as one module, though its files hold lit, esptool-js, pako and the others.

The license of every package must be one of MIT, ISC, BSD-2-Clause, BSD-3-Clause, 0BSD, Apache-2.0, Zlib, an LGPL version, GPL-2.0-or-later, GPL-3.0-or-later or MPL-2.0, read as an SPDX expression (one alternative of an `OR`, every part of an `AND`); any other license, an expression with `WITH`, a package without a license, or a package without a license text fails the build, and with it CI. A package that ships no license text but names an allowed license gets the text of its repository for that version only, from `LICENSES/web/` (see `LICENSES/README.md`).

The firmware version rules do not change: only tags of the form `vX.Y.Z` count, so `web-v` tags never change a firmware version.

## Security

- **Untrusted text.** File content, board replies and the manifest are untrusted. The app shows their text only as text, never as HTML, and never builds a link or an address from it. Previews draw pixels on a canvas.
- **Content Security Policy.** Pages cannot send headers, so the page carries the policy in a `<meta>` tag: scripts, images and fonts only from the site itself, styles from the site itself and inline (Radix inserts a `<style>` element while a dialog is open), connections only to the site itself and to WebSockets on any host (`ws:`), since a board's address is not known in advance (`wss:` is added once a board serves it), no plugins (`object-src 'none'`), no `<base>` change (`base-uri 'none'`), and no inline scripts.
- **Dependencies.** Every library is bundled into the site at build time; the published page loads nothing from other servers. Versions are pinned exactly, `package-lock.json` is committed, CI installs with `npm ci`, and dependency install scripts never run (`ignore-scripts=true` in `web/.npmrc`). Dependabot proposes updates weekly.
- **Board access.** The browser lets the page use a serial port only after the user picks it. After a first install the app reopens only the port the user picked in ESP Web Tools. The simulator accepts WebSocket connections only from the origins listed in the protocol, and has no authentication, as the protocol says. A board on WiFi accepts the app's origin; the token is kept in the browser's storage for that board and sent only as an HMAC.
- **Deployment permissions.** The deployment job has only `pages: write` and `id-token: write`; the jobs that create releases are the only ones with `contents: write`.

## Tests

Each layer is tested where it can be tested best; the test files in `web/test/` (Vitest) and `web/e2e/` (Playwright) name every case.

- **Engine:** the whole conformance suite (`conformance/valid`, `invalid`, `playlist/valid`, `playlist/invalid`, `schedule/valid`, `schedule/invalid`) with the rules of `conformance/README.md`, the brightness rule from `conformance/brightness.json`, and the winner and resolver rows of `conformance/schedule/winner.json` and `conformance/schedule/resolver.json`, which the C++ tests read too.
- **YAML:** the conversion gives the bytes of `make data` for every repository file, and the YAML 1.1 rules above have their own cases.
- **Files section:** unit tests of the summary line in every list and settings state, and of the stored choice (closed by default, only `open` reads as open, blocked storage).
- **What to play:** the resolver rows of `conformance/schedule/resolver.json` against the app's twin of the board's resolver, the words of the Automatic card (the site's choice, the board's own rule, what a deletion changes), the words of Automatic, taken from `status.play` alone (the schedule followed, the playlists followed, a choice the board cannot follow, no choice), the `play` kind of the protocol client, the play file validation against `conformance/play/`, the manifest's `play` list, and the play file after a USB install, with a refused, a cancelled and a failed install sending none.
- **Network login and the WiFi address:** unit tests of the HMAC answer (a value worked out outside the code, with Node's `crypto`), the token and nonce rules, the client's login against a scripted board (once per connection, never the token on the link, a refused token, no token given) and the board address rules.
- **Protocol client, upload queue, Delete everything, missing animations, editor state:** unit tests against a scripted fake board or the plain data: framing, retries and upload recovery, the queue's plan (what is missing, identical or different, the order, the space arithmetic, where a playlist's animations come from) and its run (questions, refusals, cancel, the lock, resume), `deleteAll` with and without the reset, what a playlist misses, and every save state of the editor with its copies and the leave-the-page question.
- **End to end:** Playwright drives the built app in Chromium against the simulator started with `--ws` on a temporary data folder, for every view and every flow above that reaches the board: uploads and installs through the queue, Delete everything from both views, the missing-animation marks and **Install missing**, the Files section (the summary in both its forms, with What to play and with the active playlist of a firmware older than schedules; the toggle and its remembered choice, the automatic openings, the uploads that must not open it such as one the board refuses, the missing-animations warning with several playlists, and long names and IDs wrapping on a phone), the playlist editor (pointer, touch and keyboard reordering, the edge scroll, focus and announcements), What to play, with the site's choice (a test writes the simulator's play file before the page connects, with a playlist the board stores but cannot play), My choice in both segments and the time settings (the simulator's `--date` gives the board a local date), the editor's save state, and the theme. The simulator's `--ws-transport wifi` stands for a board over WiFi: the end-to-end tests connect to it with **Connect over WiFi** and cover the login dialog, the remembered token, a refused token, the missing token, what is hidden over WiFi and the disabled reset box. A board scripted in the page covers what the simulator cannot give: a small storage, a refused file, an old firmware. Web Serial and ESP Web Tools need a real board and a user's choice of port, so they are tested by hand on a real board. The installation of the animations after a first install is tested end to end with a closing ESP Web Tools dialog drawn by the test and a serial port the test bridges to the simulator: the files arrive and the play file is the last upload, a firmware older than schedules gets neither the schedule nor the play file, a firmware without `formats.play` gets no play file, the box skips them, a dialog closed before its installation finished does nothing, and a board that never answers gets the alert.
- **USB connection failures:** unit tests use a simulated serial port with Chrome's rules (it cannot open twice, and it cannot close while a stream is locked) and cover a board that never answers, garbage lines, a write that never completes, a cancelled connection and a port the page still holds. End to end, Connect board with such a port that never answers or answers garbage shows the message above and opens the port again.
- **Look:** every view and its main states are scripted once and checked at 1,280 px and 375 px wide with layout checks that need no image, with the end-to-end tests (`make web-e2e`); one main state per view is also compared with a reference image in both themes, inside the official Playwright container (`make web-screenshots`). The rules of the layout checks and the reference images are described in [`web/README.md`](../../web/README.md#screenshot-tests).

CI runs these on every pull request and on `main`, see [Continuous integration](../../README.md#continuous-integration). `make check` runs the type check, the linter and the unit tests too.
